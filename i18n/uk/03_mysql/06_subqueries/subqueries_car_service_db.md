## Карта шаблонів підзапитів (легше → складніше)

| Рівень | Шаблон | Що вивчити |
|--------|--------|-------------|
| **Легко** | `IN (SELECT …)` | Підзапит повертає колонку значень; зовнішній рядок збігається з будь-яким із них. |
| **Легко** | Скалярний `> (SELECT AVG(…))` | Підзапит повертає рівно одне значення для порівняння. |
| **Легко** | `FROM (SELECT …) AS alias` | Похідна таблиця: `SELECT` як таблиця у `FROM`. |
| **Легко** | `EXISTS (SELECT 1 …)` | Істина, якщо підзапит повертає хоча б один рядок. |
| **Складно** | **Корельований** підзапит | Внутрішній `SELECT` посилається на колонку зовнішнього рядка. |
| **Складно** | `NOT EXISTS` | Рядки, для яких **немає** жодного збігу в підзапиті. |
| **Складно** | Вкладені `IN` | Внутрішні запити подають дані до зовнішніх; пам'ятайте про `NULL` у `NOT IN`. |
| **Складно** | Підзапит у `HAVING` | Порівняти агрегат з числом, що його повертає інший `SELECT`. |
| **Складно** | Корельований `EXISTS` з `JOIN` | Підзапит з'єднує таблиці, щоб перевірити умову для зовнішнього рядка. |

## Вправа E1 — `WHERE … IN (SELECT …)` (не корельований)

### Контекст

Диспетчеру потрібні всі замовлення, прив'язані до **перших 150 авто**, які коли-небудь реєстрували в сервісі — наприклад, для аудиту тривалості робіт по «найстарішим» клієнтам. У `work_orders` немає поля `vehicle.first_seen`, тож шукаємо відповідні `vehicle.id` у підзапиті.

### Чого ви навчитеся

- Не корельований підзапит, що повертає **список** значень.
- Вживання `IN (SELECT …)` для семантики «ця колонка — одне з тих».
- Утримування обох запитів швидкими через `BETWEEN`.

### Задіяні таблиці

| Таблиця | Колонки |
|---|---|
| `work_orders` | `id`, `vehicle_id`, `status`, `total_cost` |
| `vehicles` | `id` |

### Завдання

Повернути `id`, `vehicle_id`, `status`, `total_cost` із `work_orders` для рядків, де `vehicle_id` належить зрізу `vehicles.id BETWEEN 1 AND 150`, а зовнішній `work_orders.id BETWEEN 1 AND 5000`. Обмежити 25 рядками.

### Очікуваний результат (реальні рядки з дампу)

```text
+----+------------+---------------+------------+
| id | vehicle_id | status        | total_cost |
+----+------------+---------------+------------+
|  1 |          1 | new           |     500.10 |
|  2 |          2 | in_progress   |     500.20 |
|  3 |          3 | waiting_parts |     500.30 |
|  4 |          4 | completed     |     500.40 |
|  5 |          5 | cancelled     |     500.50 |
| ...|            |               |            |
| 25 |         25 | cancelled     |     502.50 |
+----+------------+---------------+------------+
```

### Підказка

Підзапит повертає одну колонку `vehicle.id`; обгорніть її в `IN (...)`.

### Розв'язання

```sql
SELECT wo.id,
       wo.vehicle_id,
       wo.status,
       wo.total_cost
FROM work_orders AS wo
WHERE wo.vehicle_id IN (
  SELECT v.id
  FROM vehicles AS v
  WHERE v.id BETWEEN 1 AND 150
)
  AND wo.id BETWEEN 1 AND 5000
LIMIT 25;
```

### Покрокове пояснення

1. **Внутрішній запит** `SELECT v.id FROM vehicles WHERE v.id BETWEEN 1 AND 150` повертає до 150 значень `vehicle.id`. Він **не корельований** — не посилається на зовнішній рядок `wo`, тому MySQL виконає його раз і перевикористає результат.
2. **`wo.vehicle_id IN (…)`** залишає лише замовлення, чий `vehicle_id` є в цьому списку — це semi-join.
3. **`AND wo.id BETWEEN 1 AND 5000`** обмежує зовнішнє сканування — інакше довелося б торкнутися всіх 100 000 рядків.
4. **Пастка з `NULL`:** якщо внутрішній список містив би `NULL` і ви вживали б `NOT IN`, предикат став би `NULL` — і не повернув би жодного рядка. Завжди додавайте `IS NOT NULL` всередину перед `NOT IN`.

## Вправа E2 — Скалярний підзапит (`SELECT AVG(…)`) у порівнянні

### Контекст

Бухгалтер хоче побачити **квитанції, вищі за середній чек** у зрізі з останніх 80 000 замовлень — щоб з'ясувати, чому вони такі дорогі. «Вище середнього» рахуємо **в межах того ж зрізу**, а не по всій таблиці.

### Чого ви навчитеся

- Підзапит, що повертає рівно одне значення (**скалярний**).
- Уживання скаляра і в `SELECT` (показати поріг), і в `WHERE` (фільтр).
- Чому MySQL спокійно обчислює середнє лише один раз.

### Задіяні таблиці

| Таблиця | Колонки |
|---|---|
| `work_orders` | `id`, `total_cost` |

### Завдання

Для `work_orders.id BETWEEN 1 AND 80000` повернути `id`, `total_cost` і `slice_avg_cost` (середнє по тому ж зрізу). Залишити рядки з `total_cost >= slice_avg_cost`. Відсортувати за `total_cost` у спадному порядку. Ліміт 20.

### Очікуваний результат (реальні рядки з дампу)

```text
+-------+------------+----------------+
| id    | total_cost | slice_avg_cost |
+-------+------------+----------------+
| 49999 |    5499.90 |    2624.987500 |
| 49998 |    5499.80 |    2624.987500 |
| 49997 |    5499.70 |    2624.987500 |
| 49996 |    5499.60 |    2624.987500 |
| 49995 |    5499.50 |    2624.987500 |
| ...   |            |                |
| 49980 |    5498.00 |    2624.987500 |
+-------+------------+----------------+
```

### Підказка

Підзапит `(SELECT AVG(total_cost) FROM work_orders WHERE id BETWEEN 1 AND 80000)` повертає одне число. Використайте його двічі: як колонку в `SELECT` і як праву частину `>=`.

### Розв'язання

```sql
SELECT wo.id,
       wo.total_cost,
       (SELECT AVG(w2.total_cost)
        FROM work_orders AS w2
        WHERE w2.id BETWEEN 1 AND 80000) AS slice_avg_cost
FROM work_orders AS wo
WHERE wo.id BETWEEN 1 AND 80000
  AND wo.total_cost >= (
        SELECT AVG(w3.total_cost)
        FROM work_orders AS w3
        WHERE w3.id BETWEEN 1 AND 80000
      )
ORDER BY wo.total_cost DESC
LIMIT 20;
```

### Покрокове пояснення

1. **Скалярний підзапит у `SELECT`** — `(SELECT AVG(…) FROM …)` мусить повернути рівно **один рядок з однією колонкою**. Інакше MySQL кидає `Subquery returns more than 1 row`.
2. **Той самий підзапит у `WHERE`** — записано двічі для читабельності; MySQL уміє згорнути такий дублікат до одного обчислення. За бажанням можна винести скаляр у похідну таблицю і зробити `JOIN`.
3. **`ORDER BY total_cost DESC`** робить «верхівку над середнім» осмисленою.
4. **Пастка — одно-прохідні vs вкладені агрегати:** не можна писати `WHERE total_cost >= AVG(total_cost)`. `WHERE` працює до групування, тому агрегат не має над чим рахуватися. Скалярний підзапит — стандартний обхід.

## Вправа E3 — Похідна таблиця у `FROM (SELECT … GROUP BY …) AS alias`

### Контекст

CRM-дашборд хоче віджет «клієнти та розмір їхнього автопарку»: скільки авто записано на кожного. Похідна таблиця спочатку групує авто, а потім приєднується до `customers` за іменем.

### Чого ви навчитеся

- Сприймати `SELECT` як віртуальну таблицю у `FROM`.
- Попередньо агрегувати в підзапиті, а потім приєднуватись для отримання підписів.
- Чому це класична альтернатива віконним функціям у старіших MySQL.

### Задіяні таблиці

| Таблиця | Колонки |
|---|---|
| `vehicles` | `id`, `customer_id` |
| `customers` | `id`, `last_name` |

### Завдання

У похідній таблиці `vc` згрупувати `vehicles` (`id BETWEEN 1 AND 10000`, `customer_id IS NOT NULL`) за `customer_id`, порахувати рядки як `vehicle_n`. Зджойнити з `customers`, повернути `customer_id`, `last_name`, `vehicle_n`. Відсортувати за `vehicle_n DESC, customer_id`. Ліміт 20.

### Очікуваний результат (реальні рядки з дампу)

```text
+-------------+------------+-----------+
| customer_id | last_name  | vehicle_n |
+-------------+------------+-----------+
|           1 | Surname_1  |         1 |
|           2 | Surname_2  |         1 |
|           3 | Surname_3  |         1 |
|           4 | Surname_4  |         1 |
|           5 | Surname_5  |         1 |
| ...         |            |           |
|          20 | Surname_20 |         1 |
+-------------+------------+-----------+
```

### Підказка

Загорніть `GROUP BY` у `FROM (…) AS vc`, далі `INNER JOIN customers AS c ON c.id = vc.customer_id`.

### Розв'язання

```sql
SELECT vc.customer_id,
       c.last_name,
       vc.vehicle_n
FROM (
       SELECT customer_id,
              COUNT(*) AS vehicle_n
       FROM vehicles
       WHERE id BETWEEN 1 AND 10000
         AND customer_id IS NOT NULL
       GROUP BY customer_id
     ) AS vc
INNER JOIN customers AS c ON c.id = vc.customer_id
WHERE vc.vehicle_n >= 1
ORDER BY vc.vehicle_n DESC, vc.customer_id
LIMIT 20;
```

### Покрокове пояснення

1. **Похідна таблиця** `vc` будується першою: для кожного `customer_id` у зрізі рахуємо авто. Далі вона використовується як звичайна таблиця.
2. **`INNER JOIN customers`** додає `last_name`. Без нього у нас лише зовнішній ключ.
3. **`AS vc` є обов'язковим** — у MySQL кожна похідна таблиця в `FROM` повинна мати псевдонім; інакше синтаксична помилка.
4. **Двоключове `ORDER BY`** робить порядок детермінованим. Без `customer_id` як другого ключа рядки з однаковим `vehicle_n` могли б іти в будь-якому порядку.
5. **Чому не віконна функція?** `COUNT(*) OVER (PARTITION BY customer_id)` теж спрацює в MySQL 8+, але похідна таблиця переноситься на старіші движки й простіша для розуміння.

## Вправа E4 — `EXISTS (SELECT 1 …)`

### Контекст

Маркетинг хоче надіслати «дякуємо»-купон кожному клієнту з пакету ранніх id (`1..500`), хто **колись залишав фідбек**. Що саме було у відгуку — байдуже, важливий сам факт існування рядка.

### Чого ви навчитеся

- `EXISTS` як логічний тест: «чи повертає внутрішній запит хоч один рядок?»
- Чому пишуть `SELECT 1` усередині `EXISTS` — список колонок не має значення.
- Чому `EXISTS` часто швидший за `IN (SELECT …)`, коли внутрішня таблиця велика.

### Задіяні таблиці

| Таблиця | Колонки |
|---|---|
| `customers` | `id`, `first_name`, `last_name` |
| `feedback` | `id`, `customer_id` |

### Завдання

Повернути `id`, `first_name`, `last_name` клієнтів з `id BETWEEN 1 AND 500`, для яких існує хоча б один рядок у `feedback` (також обмежений `f.id BETWEEN 1 AND 200000`). Ліміт 30.

### Очікуваний результат (реальні рядки з дампу)

```text
+----+------------+------------+
| id | first_name | last_name  |
+----+------------+------------+
|  1 | Name_1     | Surname_1  |
|  2 | Name_2     | Surname_2  |
|  3 | Name_3     | Surname_3  |
|  4 | Name_4     | Surname_4  |
|  5 | Name_5     | Surname_5  |
| ...|            |            |
| 30 | Name_30    | Surname_30 |
+----+------------+------------+
```

### Підказка

`EXISTS (SELECT 1 FROM feedback WHERE customer_id = c.id …)`. Внутрішній `WHERE` посилається на `c.id` із зовнішнього запиту — саме це робить тест «для цього клієнта».

### Розв'язання

```sql
SELECT c.id,
       c.first_name,
       c.last_name
FROM customers AS c
WHERE c.id BETWEEN 1 AND 500
  AND EXISTS (
    SELECT 1
    FROM feedback AS f
    WHERE f.customer_id = c.id
      AND f.id BETWEEN 1 AND 200000
  )
LIMIT 30;
```

### Покрокове пояснення

1. **`EXISTS (…)`** зупиняє сканування внутрішнього запиту, щойно знаходить перший збіг, — тому він дешевий на зв'язках «один-до-багатьох».
2. **`SELECT 1`** — ідіома: `SELECT *`, `SELECT f.id`, `SELECT NULL` дають той самий ефект. Важливий лише факт наявності рядка.
3. **Внутрішнє `f.customer_id = c.id`** — це кореляція: коли зовнішній курсор переходить на нового клієнта, внутрішній запит фактично перевиконується для нового `c.id`.
4. **Порівняння з `IN`:** `c.id IN (SELECT customer_id FROM feedback …)` теж працює. Вибирайте `EXISTS`, коли внутрішня таблиця велика — він зупиняється на першому збігу.

## Вправа H1 — Корельований шаблон зі скалярним глобальним середнім

### Контекст

Та ж ідея «вище середнього», що й у E2, але масштабніша: керівник операцій хоче подивитися на **25 найдорожчих замовлень у перших 8 000** разом з **глобальним середнім** по значно більшому зрізі. Він на око порівняє розрив.

### Чого ви навчитеся

- Скалярний підзапит, що покриває ширший зріз, ніж зовнішній запит.
- Різницю між **корельованим** і **не корельованим** скалярним підзапитом. (Цей не корельований, але показує форму.)
- Сортувати за зовнішнім стовпцем, поки константа з підзапита «їде поруч».

### Задіяні таблиці

| Таблиця | Колонки |
|---|---|
| `work_orders` | `id`, `assigned_mechanic_id`, `total_cost` |

### Завдання

Для `wo.id BETWEEN 1 AND 8000` з `total_cost IS NOT NULL` повернути `id`, `assigned_mechanic_id`, `total_cost` і `global_avg_cost` зі скалярного підзапита по `work_orders.id BETWEEN 1 AND 200000`. Відсортувати за `total_cost` у спадному порядку. Ліміт 25.

### Очікуваний результат (реальні рядки з дампу)

```text
+------+----------------------+------------+-----------------+
| id   | assigned_mechanic_id | total_cost | global_avg_cost |
+------+----------------------+------------+-----------------+
| 8000 |                 8000 |    1300.00 |     2999.950000 |
| 7999 |                 7999 |    1299.90 |     2999.950000 |
| 7998 |                 7998 |    1299.80 |     2999.950000 |
| 7997 |                 7997 |    1299.70 |     2999.950000 |
| 7996 |                 7996 |    1299.60 |     2999.950000 |
| ...  |                      |            |                 |
| 7976 |                 7976 |    1297.60 |     2999.950000 |
+------+----------------------+------------+-----------------+
```

### Підказка

Скаляр `(SELECT AVG(...) FROM work_orders WHERE id BETWEEN 1 AND 200000)` повертає одне і те саме число для кожного рядка — обчислюється один раз.

### Розв'язання

```sql
SELECT wo.id,
       wo.assigned_mechanic_id,
       wo.total_cost,
       (SELECT AVG(wb.total_cost)
        FROM work_orders AS wb
        WHERE wb.id BETWEEN 1 AND 200000) AS global_avg_cost
FROM work_orders AS wo
WHERE wo.id BETWEEN 1 AND 8000
  AND wo.total_cost IS NOT NULL
ORDER BY wo.total_cost DESC
LIMIT 25;
```

### Покрокове пояснення

1. **Скалярний підзапит у `SELECT`** проектує однакове `global_avg_cost` на кожен рядок — зручно для дашбордів, де кожен рядок повинен «знати» свій базовий рівень.
2. **Не корельований**: внутрішній запит не посилається на `wo`, тож виконується один раз. Щоб зробити його **корельованим**, замініть зовнішнє `BETWEEN` на щось на кшталт `WHERE wb.assigned_mechanic_id = wo.assigned_mechanic_id` — див. H4 для цього шаблону.
3. **`total_cost IS NOT NULL`** оберігає від відсутніх значень, які інакше зіпсували б порядок сортування.
4. **Швидкість:** без індексів по `id` зріз доводилося б сканувати; з PRIMARY KEY MySQL використовує range scan.

## Вправа H2 — `NOT EXISTS`

### Контекст

Прапор контролю якості: показати клієнтів, у яких **немає** «сторожової» відмітки в `feedback` (рейтинг `999`, який використовують як службовий tombstone). У дампі такого рейтингу не існує — тож запит фактично повертає «всіх клієнтів зі зрізу», що добре для демонстрації форми без сюрпризів.

### Чого ви навчитеся

- `NOT EXISTS` для anti-semi-join.
- Чому `NOT EXISTS` безпечніший за `NOT IN`, коли внутрішня колонка може бути `NULL`.
- Передбачуваний вироджений випадок: внутрішній предикат, що ніколи не спрацьовує.

### Задіяні таблиці

| Таблиця | Колонки |
|---|---|
| `customers` | `id`, `first_name`, `last_name` |
| `feedback` | `customer_id`, `rating` |

### Завдання

Повернути `id`, `first_name`, `last_name` клієнтів з `id BETWEEN 1 AND 300`, у яких **немає** жодного рядка `feedback` з `rating = 999`. Ліміт 30.

### Очікуваний результат (реальні рядки з дампу)

```text
+----+------------+------------+
| id | first_name | last_name  |
+----+------------+------------+
|  1 | Name_1     | Surname_1  |
|  2 | Name_2     | Surname_2  |
|  3 | Name_3     | Surname_3  |
|  4 | Name_4     | Surname_4  |
|  5 | Name_5     | Surname_5  |
| ...|            |            |
| 30 | Name_30    | Surname_30 |
+----+------------+------------+
```

### Підказка

`NOT EXISTS` віддзеркалює `EXISTS`: інвертуємо зовнішній предикат, той самий корельований внутрішній.

### Розв'язання

```sql
SELECT c.id,
       c.first_name,
       c.last_name
FROM customers AS c
WHERE c.id BETWEEN 1 AND 300
  AND NOT EXISTS (
    SELECT 1
    FROM feedback AS f
    WHERE f.customer_id = c.id
      AND f.rating = 999
  )
LIMIT 30;
```

### Покрокове пояснення

1. **`NOT EXISTS`** істинний, коли внутрішній запит повертає **нуль рядків**. У реальних даних замість `f.rating = 999` зазвичай стоїть змістовний предикат — наприклад, `f.rating IS NULL` або `f.created_at < '2020-01-01'`.
2. **`f.rating = 999`** ніколи не спрацьовує у цьому дампі (рейтинги `1..5`), тож усі клієнти зі зрізу проходять фільтр — корисно для демонстрації **форми** без зайвих відволікань.
3. **Чому `NOT EXISTS`, а не `NOT IN`?** Коли внутрішній `SELECT` може повернути `NULL`, `NOT IN (NULL, …)` стане `NULL` і тихо викине рядок. `NOT EXISTS` `NULL`-безпечний за визначенням.
4. **Типовий баг:** забути кореляцію `f.customer_id = c.id`. Без неї внутрішній запит питає «чи існує *десь* рядок з `rating = 999`?» — це зовсім інша семантика.

## Вправа H3 — Вкладений `IN` через довідкову таблицю

### Контекст

HR потрібен список контактів кожного механіка з пакету ранніх id (`employees.id BETWEEN 1 AND 2000`). «Механік» — це не колонка `employees`; «механік» — це `title` у довіднику `roles`. Виштовхуємо фільтр за `title` у підзапит на `roles` і передаємо знайдені `role_id` назовні.

### Чого ви навчитеся

- Як шукати сурогатний ключ через довідник.
- Уживати `LIKE '%Mechanic%'` для «розмитих» назв посад.
- Чому такий шаблон зручніший за `JOIN`, коли з довідника не потрібні колонки.

### Задіяні таблиці

| Таблиця | Колонки |
|---|---|
| `employees` | `id`, `first_name`, `last_name`, `role_id` |
| `roles` | `id`, `title` |

### Завдання

Повернути `id`, `first_name`, `last_name`, `role_id` працівників з `id BETWEEN 1 AND 2000`, чий `role_id` належить ролям з `title LIKE '%Mechanic%'`. Ліміт 25.

### Очікуваний результат (реальні рядки з дампу)

```text
+-----+-------------+----------------+---------+
| id  | first_name  | last_name      | role_id |
+-----+-------------+----------------+---------+
|   1 | EmpName_1   | EmpSurname_1   |       1 |
|  11 | EmpName_11  | EmpSurname_11  |       1 |
|  21 | EmpName_21  | EmpSurname_21  |       1 |
|  31 | EmpName_31  | EmpSurname_31  |       1 |
|  41 | EmpName_41  | EmpSurname_41  |       1 |
| ... |             |                |         |
| 241 | EmpName_241 | EmpSurname_241 |       1 |
+-----+-------------+----------------+---------+
```

### Підказка

Внутрішній запит: `SELECT r.id FROM roles WHERE r.title LIKE '%Mechanic%'`. Підставте в `e.role_id IN (...)`.

### Розв'язання

```sql
SELECT e.id,
       e.first_name,
       e.last_name,
       e.role_id
FROM employees AS e
WHERE e.id BETWEEN 1 AND 2000
  AND e.role_id IN (
    SELECT r.id
    FROM roles AS r
    WHERE r.title LIKE '%Mechanic%'
  )
LIMIT 25;
```

### Покрокове пояснення

1. **Внутрішній запит** повертає невелику множину `role.id` для ролей, чий `title` містить `Mechanic`. Оскільки `roles` крихітний, MySQL хешує результат і ефективно перевіряє `e.role_id`.
2. **`LIKE '%Mechanic%'`** має ведучий `%`, тож **не може** використати звичайний B-tree індекс. Тут це не проблема (таблиця маленька), але той самий шаблон на 100-мільйонній таблиці буде повільним.
3. **Аналог через `JOIN`:** `INNER JOIN roles r ON r.id = e.role_id WHERE r.title LIKE '%Mechanic%'`. Беріть `JOIN`, коли потрібні колонки з `roles`; беріть `IN` — коли ні.
4. **А чому не `EXISTS`?** Обидва спрацюють. `IN` тут читається природніше, бо внутрішнє джерело — мала фіксована множина.

## Вправа H4 — Підзапит у `HAVING` (агрегат проти похідної константи)

### Контекст

Сервіс хоче бачити **завантажених механіків** — тих, у кого сумарне навантаження на зрізі замовлень не менше за **середнє навантаження на одного механіка** в тому ж зрізі. «Середнє навантаження» — це агрегат над агрегатом, тому обчислюємо його в похідному підзапиті, а порівнюємо в `HAVING`.

### Чого ви навчитеся

- Як спочатку агрегувати, а потім порівнювати агрегат з іншим агрегатом.
- Вкладати `SELECT COUNT(*) … GROUP BY …` всередину `SELECT AVG(cnt)`.
- Уживати `HAVING` для фільтрації груп за обчисленим порогом.

### Задіяні таблиці

| Таблиця | Колонки |
|---|---|
| `work_orders` | `id`, `assigned_mechanic_id` |

### Завдання

Для `work_orders.id BETWEEN 1 AND 100000` з `assigned_mechanic_id IS NOT NULL` згрупувати за `assigned_mechanic_id` і порахувати. Залишити лише механіків, у кого кількість `>=` середньої кількості на одного механіка в тому ж зрізі. Відсортувати за `wo_cnt DESC`. Ліміт 15.

### Очікуваний результат (реальні рядки з дампу)

```text
+----------------------+--------+
| assigned_mechanic_id | wo_cnt |
+----------------------+--------+
|                94898 |      1 |
|                94899 |      1 |
|                94900 |      1 |
|                94901 |      1 |
|                94902 |      1 |
| ...                  |        |
|                94912 |      1 |
+----------------------+--------+
```

### Підказка

Обгорніть кількість на механіка в інший `SELECT AVG(cnt)`, потім порівняйте в `HAVING COUNT(*) >= (…)`.

### Розв'язання

```sql
SELECT wo.assigned_mechanic_id,
       COUNT(*) AS wo_cnt
FROM work_orders AS wo
WHERE wo.id BETWEEN 1 AND 100000
  AND wo.assigned_mechanic_id IS NOT NULL
GROUP BY wo.assigned_mechanic_id
HAVING COUNT(*) >= (
  SELECT AVG(cnt)
  FROM (
         SELECT COUNT(*) AS cnt
         FROM work_orders AS w2
         WHERE w2.id BETWEEN 1 AND 100000
           AND w2.assigned_mechanic_id IS NOT NULL
         GROUP BY w2.assigned_mechanic_id
       ) AS per_mechanic
)
ORDER BY wo_cnt DESC
LIMIT 15;
```

### Покрокове пояснення

1. **Внутрішня похідна таблиця** `per_mechanic` повертає по рядку на механіка з його кількістю. `SELECT AVG(cnt) FROM per_mechanic` згортає це до одного числа — середнє навантаження.
2. **`HAVING COUNT(*) >= (…)`** фільтрує **групи** після `GROUP BY`. `WHERE COUNT(*) >= …` — синтаксична помилка.
3. **У цьому дампі** в кожного механіка приблизно однакова кількість (~1), тож середнє теж ~1 і більшість проходить — результат демонструє **форму**, а не різке відсіювання.
4. **Типова помилка:** забути псевдонім `AS per_mechanic` — MySQL вимагає назву для кожного підзапита у `FROM`.

## Вправа H5 — Корельований `EXISTS` із `JOIN` усередині

### Контекст

Адміністратор хоче список клієнтів, у яких **є щонайменше один підтверджений запис на сервіс**. Прямого зв'язку між `customers` і `appointments` немає — він проходить через `vehicles`. Найчистіший спосіб — `EXISTS` з невеликим внутрішнім `JOIN`.

### Чого ви навчитеся

- Поєднання `EXISTS` з багатотабличним джоїном усередині.
- Кореляція через два рівні: зовнішній `customers.id` ↔ внутрішній `vehicles.customer_id`.
- Перевага `EXISTS` над `INNER JOIN … GROUP BY`, коли важливо уникнути дублювання рядків.

### Задіяні таблиці

| Таблиця | Колонки |
|---|---|
| `customers` | `id`, `first_name`, `last_name` |
| `vehicles` | `id`, `customer_id` |
| `appointments` | `id`, `vehicle_id`, `status` |

### Завдання

Повернути `id`, `first_name`, `last_name` клієнтів з `id BETWEEN 1 AND 400`, для яких існує хоча б один рядок у `vehicles JOIN appointments`, де авто належить клієнту, статус запису `confirmed`, а `appointments.id BETWEEN 1 AND 200000`. Ліміт 25.

### Очікуваний результат (реальні рядки з дампу)

```text
+----+------------+------------+
| id | first_name | last_name  |
+----+------------+------------+
|  2 | Name_2     | Surname_2  |
|  6 | Name_6     | Surname_6  |
| 10 | Name_10    | Surname_10 |
| 14 | Name_14    | Surname_14 |
| 18 | Name_18    | Surname_18 |
| ...|            |            |
| 98 | Name_98    | Surname_98 |
+----+------------+------------+
```

### Підказка

Усередині `EXISTS` зробіть `INNER JOIN vehicles … appointments` і скорелюйте `v.customer_id = c.id`.

### Розв'язання

```sql
SELECT c.id,
       c.first_name,
       c.last_name
FROM customers AS c
WHERE c.id BETWEEN 1 AND 400
  AND EXISTS (
    SELECT 1
    FROM vehicles AS v
    INNER JOIN appointments AS a ON a.vehicle_id = v.id
    WHERE v.customer_id = c.id
      AND a.status = 'confirmed'
      AND a.id BETWEEN 1 AND 200000
  )
LIMIT 25;
```

### Покрокове пояснення

1. **Кореляція на два рівні:** внутрішнє `WHERE v.customer_id = c.id` зв'язує підзапит із зовнішнім клієнтом. Для кожного кандидата `c` MySQL виконує внутрішній джоїн.
2. **`INNER JOIN` усередині `EXISTS`** — нормально: важливий лише факт повернення рядка. Результат джоїна не передається назовні.
3. **`a.status = 'confirmed'`** — рівність на маленькому enum-подібному домені.
4. **Чому не `SELECT DISTINCT c.id … JOIN …`?** Теж спрацює, але повертає проміжний результат, який треба дедуплікувати. `EXISTS` чесніше виражає «є хоч один збіг».
5. **Зверніть увагу на результат** — лише кожен 4-й клієнт (тут `id MOD 4 = 2`) має підтверджений запис у перших 200 000, рівно так дамп і генерувався.

## Поради при порожньому або повільному підзапиті

| Симптом | Імовірне виправлення |
|---|---|
| `Subquery returns more than 1 row` | Ваш скалярний підзапит повертає >1 рядка. Додайте `LIMIT 1` (рідко правильно) або перепишіть через `IN` / `JOIN`. |
| `NOT IN` із `NULL` нічого не повертає | Внутрішній підзапит повернув `NULL`. Додайте `WHERE col IS NOT NULL` всередині або беріть `NOT EXISTS`. |
| Корельований підзапит повільний | Додайте індекс на корелюючий стовпець або перепишіть через `JOIN` / віконну функцію. |
| `EXISTS` завжди істинний | Внутрішній запит без предиката-кореляції (`f.customer_id = c.id` відсутній). |
| Похідна таблиця без псевдоніма | MySQL вимагає `FROM (…) AS alias`. Не пропускайте `AS name`. |

Якщо хочеться прогнати **всі** приклади відразу: `mysql -t -u root car_service_db < 03_mysql/06_subqueries/car_service_subqueries_examples.sql`.
