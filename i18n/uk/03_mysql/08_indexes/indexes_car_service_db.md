# Індекси — лабораторія `car_service_db`

> Translation / Переклад: [English](../../../../03_mysql/08_indexes/indexes_car_service_db.md)

Цей модуль додає **навчальну таблицю `idx_lab`** (та маленьку `idx_geo` для `SPATIAL`) усередині **`car_service_db`**. Ви будете **`CREATE INDEX`** / **`DROP INDEX`** руками, а потім порівнюєте плани запитів і час виконання **з індексом та без нього**. Цикл «порівняти плани» — і є вся ідея цього модуля: лише так ви зрозумієте, чи дійсно MySQL використав ваш індекс.

Готові запити лежать у файлі-компаньйоні: [`08_indexes/car_service_indexes_examples.sql`](../../../../03_mysql/08_indexes/car_service_indexes_examples.sql).

```bash
mysql -u root -e "CREATE DATABASE IF NOT EXISTS car_service_db;"
gunzip -c 01_database_mysql/car_service_db.sql.gz | mysql -u root car_service_db
mysql -u root car_service_db < 03_mysql/08_indexes/car_service_indexes_examples.sql
```

**Вимоги:** MySQL **8.0+** (для функціональних індексів, `EXPLAIN ANALYZE`, descending-індексів). Усі виводи `EXPLAIN` нижче зняті на тій самій `idx_lab` (40 000 рядків, засіяних із `parts`).

## Як порівнювати швидкість вручну

1. Виконайте **базовий** `EXPLAIN` / `EXPLAIN ANALYZE` **до** створення вторинного індексу.
2. Виконайте відповідний **`CREATE INDEX`** (або розкоментуйте у скрипті).
3. Запустіть той самий `SELECT` і порівняйте:
   - У `EXPLAIN` стовпець `type` повинен змінитися з **`ALL`** (повний скан) на **`ref`**, **`range`** або **`const`**.
   - `EXPLAIN ANALYZE` (8.0.18+) показує фактичний час і прочитані рядки — це найкорисніше для відповіді «чи стало справді швидше?».
4. Для повторного «холодного» тесту видаліть індекс і повторіть запит:
   ```sql
   DROP INDEX ix_bt_ref ON idx_lab;
   ```
5. Опційно після масового завантаження або багатьох DML-операцій: `ANALYZE TABLE idx_lab;`.

**Зауваження:** `SHOW PROFILES` / `profiling` застаріли у нових MySQL; беріть **`EXPLAIN ANALYZE`** там, де є.

## Типи індексів у демонстрації (MySQL / InnoDB)

| Тип | У скрипті | Типове застосування |
|-----|-----------|----------------------|
| **Первинний ключ** | `PRIMARY KEY (id)` | Кластерне B-дерево; унікальний id рядка. |
| **Вторинний B-tree** | `CREATE INDEX ix_bt_ref ON idx_lab (ref_num)` | Рівність / діапазон по `ref_num`. |
| **UNIQUE** | `CREATE UNIQUE INDEX ix_uniq_sku ON idx_lab (sku)` | Один рядок на SKU; значення мають лишатися унікальними. |
| **Композитний** | `(status, ref_num)` | Фільтр по ведучій колонці + діапазон по наступній. |
| **Префіксний** | `sku(16)` на довгому `VARCHAR` | Індексуємо лише перші N символів — економимо місце. |
| **FULLTEXT** | `FULLTEXT (note)` | Пошук з рейтингом через `MATCH(note) AGAINST(...)`. |
| **Функціональний / виразовий** (8.0.13+) | `(LOWER(sku))` | Рівність по обчисленому виразу. |
| **SPATIAL** | `POINT` + `SPATIAL INDEX` на `idx_geo` | `MBRContains`, `ST_Within` тощо. |

**Не включено (рідко в прикладних БД):** `HASH` (тільки engine `MEMORY`), descending- та invisible-індекси (опційно — див. документацію MySQL).

## Скидання лабораторії (одноразово)

```sql
DROP TABLE IF EXISTS idx_geo;
DROP TABLE IF EXISTS idx_lab;

CREATE TABLE idx_lab (
  id      INT NOT NULL AUTO_INCREMENT,
  ref_num INT NOT NULL,
  sku     VARCHAR(80) NOT NULL,
  note    TEXT,
  status  VARCHAR(20) NOT NULL DEFAULT 'open',
  PRIMARY KEY (id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci;

INSERT INTO idx_lab (ref_num, sku, note, status)
SELECT p.id, p.sku, p.name, 'open'
FROM parts AS p
WHERE p.id BETWEEN 1 AND 40000;

SET @probe_ref := (SELECT ref_num FROM idx_lab WHERE id = 15000 LIMIT 1); -- 15000
SET @probe_sku := (SELECT sku     FROM idx_lab WHERE id = 15000 LIMIT 1); -- 'SKU-00015000'
```

40 000 рядків, поки що лише `PRIMARY KEY`. З цим базовим планом порівнюються всі «після» нижче.

## Вправа 1 — Вторинний B-tree по `ref_num`

### Контекст

`idx_lab.ref_num` дзеркалить `parts.id` із дампу. Запит «знайти за номером запчастини» (`WHERE ref_num BETWEEN 15000 AND 15005`) — один з найпоширеніших шаблонів у інтерфейсі сервісу.

### Чого ви навчитеся

- Що `WHERE col BETWEEN x AND y` без індексу робить **повний скан** (`type=ALL`).
- Що звичайний `CREATE INDEX … (col)` перемикає план на **range scan** (`type=range`).
- Як читати колонки `key`, `key_len`, `rows` у `EXPLAIN`.

### Задіяні таблиці

| Таблиця | Колонка |
|---|---|
| `idx_lab` | `ref_num` |

### Завдання

1. Запустіть `EXPLAIN` для range-запиту **до** створення вторинного індексу.
2. `CREATE INDEX ix_bt_ref ON idx_lab (ref_num);`.
3. Запустіть той самий `EXPLAIN` знову.

### Очікуваний результат (реальний `EXPLAIN`)

**До** індексу — `type=ALL`, ~40 000 рядків:

```text
+----+-------------+---------+------------+------+---------------+------+---------+------+-------+----------+-------------+
| id | select_type | table   | partitions | type | possible_keys | key  | key_len | ref  | rows  | filtered | Extra       |
+----+-------------+---------+------------+------+---------------+------+---------+------+-------+----------+-------------+
|  1 | SIMPLE      | idx_lab | NULL       | ALL  | NULL          | NULL | NULL    | NULL | 40000 |    11.11 | Using where |
+----+-------------+---------+------------+------+---------------+------+---------+------+-------+----------+-------------+
```

**Після** `CREATE INDEX ix_bt_ref … (ref_num)` — `type=range`, оцінка 6 рядків:

```text
+----+-------------+---------+------------+-------+---------------+-----------+---------+------+------+----------+-----------------------+
| id | select_type | table   | partitions | type  | possible_keys | key       | key_len | ref  | rows | filtered | Extra                 |
+----+-------------+---------+------------+-------+---------------+-----------+---------+------+------+----------+-----------------------+
|  1 | SIMPLE      | idx_lab | NULL       | range | ix_bt_ref     | ix_bt_ref | 4       | NULL |    6 |   100.00 | Using index condition |
+----+-------------+---------+------------+-------+---------------+-----------+---------+------+------+----------+-----------------------+
```

Зразок рядків з реального запиту:

```text
+-------+--------------+
| id    | sku          |
+-------+--------------+
| 15000 | SKU-00015000 |
| 15001 | SKU-00015001 |
| 15002 | SKU-00015002 |
| 15003 | SKU-00015003 |
| 15004 | SKU-00015004 |
+-------+--------------+
```

### Підказка

У `EXPLAIN` дивіться на `type`. `ALL` — повний скан таблиці; `range` — діапазонний скан по індексу; `ref` — пошук за рівністю; `const` — один рядок через PK/UNIQUE.

### Розв'язання

```sql
EXPLAIN
SELECT id, sku FROM idx_lab WHERE ref_num BETWEEN 15000 AND 15005;

CREATE INDEX ix_bt_ref ON idx_lab (ref_num);

EXPLAIN
SELECT id, sku FROM idx_lab WHERE ref_num BETWEEN 15000 AND 15005;

SELECT id, sku FROM idx_lab WHERE ref_num BETWEEN 15000 AND 15005 LIMIT 5;

-- Опційно: повторно «холодний» скан
-- DROP INDEX ix_bt_ref ON idx_lab;
```

### Покрокове пояснення

1. **`type=ALL`** означає, що MySQL читає кожен рядок і застосовує `WHERE`. На 40 000 рядках це швидко в абсолютному значенні, але повільно в перерахунку на рядок.
2. **`type=range`** — це ціль для `BETWEEN` / `IN (…)` / `>=`: індекс звужує скан до запитуваного діапазону.
3. **`key_len=4`** відповідає `INT` (4 байти). Для рядкових колонок ви побачите щось на кшталт `322` (= 80 символів × 4 байти + 2 байти на довжину для `utf8mb4`).
4. **Без індексу `Extra=Using where`** — MySQL обчислює предикат після читання. З індексом — **`Using index condition`** («ICP») зсуває предикат у storage engine, тож менше рядків матеріалізується.
5. **Trade-off:** індекси прискорюють читання, але уповільнюють запис (кожен `INSERT` / `UPDATE` оновлює B-дерево). Додавайте індекси лише під справді популярні запити.

## Вправа 2 — UNIQUE-індекс по `sku`

### Контекст

Кожен SKU має бути унікальним — це бізнес-правило. `UNIQUE`-індекс одночасно змушує дотримуватися цього обмеження і робить пошук за рівністю фактично `O(1)` (один проб по B-дереву + один fetch).

### Чого ви навчитеся

- `UNIQUE`-індекси водночас гарантують унікальність **та** пришвидшують equality-пошук.
- План `type=const`: MySQL знає, що лукап повертає максимум один рядок.
- Що буде, якщо в даних є дублікати (`CREATE` фейлиться).

### Задіяні таблиці

| Таблиця | Колонка |
|---|---|
| `idx_lab` | `sku` |

### Завдання

1. `CREATE UNIQUE INDEX ix_uniq_sku ON idx_lab (sku);`.
2. Запустіть `EXPLAIN` для пошуку за конкретним SKU; перевірте `type=const`.

### Очікуваний результат (реальний `EXPLAIN`)

```text
+----+-------------+---------+------------+-------+---------------+-------------+---------+-------+------+----------+-------+
| id | select_type | table   | partitions | type  | possible_keys | key         | key_len | ref   | rows | filtered | Extra |
+----+-------------+---------+------------+-------+---------------+-------------+---------+-------+------+----------+-------+
|  1 | SIMPLE      | idx_lab | NULL       | const | ix_uniq_sku   | ix_uniq_sku | 322     | const |    1 |   100.00 | NULL  |
+----+-------------+---------+------------+-------+---------------+-------------+---------+-------+------+----------+-------+
```

Лукап повертає рівно потрібний рядок:

```text
+----+---------+
| id | ref_num |
+----+---------+
|  1 |       1 |
+----+---------+
```

### Підказка

`type=const` — найкращий доступ після `system`: MySQL впізнає цільовий рядок за унікальним ключем і трактує його як константу.

### Розв'язання

```sql
CREATE UNIQUE INDEX ix_uniq_sku ON idx_lab (sku);

EXPLAIN
SELECT id, ref_num FROM idx_lab WHERE sku = 'SKU-00015000';

SELECT id, ref_num FROM idx_lab WHERE sku = 'SKU-00015000';

-- Демонстрація: спроба вставити дублікат тепер відкидається
-- INSERT INTO idx_lab (ref_num, sku, status) VALUES (99, 'SKU-00015000', 'open');
-- -> ERROR 1062 (23000): Duplicate entry 'SKU-00015000' for key 'idx_lab.ix_uniq_sku'

-- DROP INDEX ix_uniq_sku ON idx_lab;
```

### Покрокове пояснення

1. **`UNIQUE` — одночасно обмеження і індекс.** Усередині — B-дерево з перевіркою унікальності при вставці.
2. **`type=const`** дозволяє оптимізатору вважати лукап одно-рядковим — інші джоїни можуть будуватися на цьому.
3. **`key_len=322`** — це `VARCHAR(80)` з `utf8mb4` (`80 * 4 + 2 = 322` байти).
4. **Сценарій падіння:** якщо в даних є дублікати, `CREATE UNIQUE INDEX` фейлиться з `Duplicate entry … for key …`. Спершу почистіть дублі або використайте `CREATE INDEX` (без unique).
5. **Побічний ефект:** наступні спроби `INSERT` дубліката автоматично відкидаються — гарантію перевіряє движок, а не програма.

## Вправа 3 — Композитний індекс `(status, ref_num)`

### Контекст

Найчастіший дашбордовий запит на цьому наборі даних — «відкриті тікети у заданому діапазоні part-id». Композитний індекс, у якого **ведуча колонка `status`** і **друга `ref_num`**, може відповідати на обидва предикати лише з індекса.

### Чого ви навчитеся

- Композитні індекси впорядковані: у `WHERE` має бути **лівий префікс**, інакше індекс не задіється.
- Оптимізатор може взяти однотабличний `ix_bt_ref`, якщо вважає його дешевшим — вибір індекса cost-based, не детермінований.

### Задіяні таблиці

| Таблиця | Колонки |
|---|---|
| `idx_lab` | `status`, `ref_num` |

### Завдання

1. `CREATE INDEX ix_comp_status_ref ON idx_lab (status, ref_num);`.
2. Запустіть `EXPLAIN` запиту, який фільтрує одразу по обох колонках.

### Очікуваний результат (реальний `EXPLAIN`)

Поряд із `ix_bt_ref` MySQL обирає той, що, на його думку, дешевший — тут це звичайний `ix_bt_ref`:

```text
+----+-------------+---------+------------+-------+------------------------------+-----------+---------+------+------+----------+------------------------------------+
| id | select_type | table   | partitions | type  | possible_keys                | key       | key_len | ref  | rows | filtered | Extra                              |
+----+-------------+---------+------------+-------+------------------------------+-----------+---------+------+------+----------+------------------------------------+
|  1 | SIMPLE      | idx_lab | NULL       | range | ix_bt_ref,ix_comp_status_ref | ix_bt_ref | 4       | NULL |  501 |   100.00 | Using index condition; Using where |
+----+-------------+---------+------------+-------+------------------------------+-----------+---------+------+------+----------+------------------------------------+
```

Зразок рядків:

```text
+-------+--------------+---------+
| id    | sku          | ref_num |
+-------+--------------+---------+
| 10000 | SKU-00010000 |   10000 |
| 10001 | SKU-00010001 |   10001 |
| 10002 | SKU-00010002 |   10002 |
| 10003 | SKU-00010003 |   10003 |
| 10004 | SKU-00010004 |   10004 |
+-------+--------------+---------+
```

### Підказка

`possible_keys` показує всі кандидати; `key` — обраний. Щоб «змусити» взяти композитний — `FORCE INDEX (ix_comp_status_ref)` (тільки для діагностики).

### Розв'язання

```sql
CREATE INDEX ix_comp_status_ref ON idx_lab (status, ref_num);

EXPLAIN
SELECT id, sku, ref_num
FROM idx_lab
WHERE status = 'open'
  AND ref_num BETWEEN 10000 AND 10500
LIMIT 50;

SELECT id, sku, ref_num
FROM idx_lab
WHERE status = 'open'
  AND ref_num BETWEEN 10000 AND 10500
LIMIT 5;

EXPLAIN
SELECT id, sku, ref_num
FROM idx_lab FORCE INDEX (ix_comp_status_ref)
WHERE status = 'open'
  AND ref_num BETWEEN 10000 AND 10500;

-- DROP INDEX ix_comp_status_ref ON idx_lab;
```

### Покрокове пояснення

1. **Правило лівого префікса.** Композитний індекс `(a, b)` пришвидшує `a` або `a AND b`, але **не** окремий `b` — B-дерево впорядковане спершу по `a`.
2. **У цій лабі всі рядки мають `status='open'`.** Кардинальність 1, тож MySQL розуміє, що композитний індекс не допомагає, і бере `ix_bt_ref`. Запускайте `ANALYZE TABLE idx_lab;` після великих змін, щоб освіжити статистику.
3. **Коли композитний виграє?** Коли `status` справді **селективний** (наприклад, лише 5 % рядків `cancelled`), композитний індекс дозволяє MySQL пропустити 95 % таблиці.
4. **Колонки-підказки:** `possible_keys` — кандидати, `key` — вибір, `key_len` — скільки байтів ведучих колонок задіяно (тут 4 байти = лише перший `int`).

## Вправа 4 — Префіксний індекс `sku(16)`

### Контекст

`sku` — це `VARCHAR(80)`, але вже перші 8-10 символів унікальні. Індексувати лише перші 16 байтів — це економія місця й пам'яті при майже тій самій швидкості.

### Чого ви навчитеся

- Синтаксис `(col(N))` — індекс по **байтовому префіксу** рядкової колонки.
- Компроміс між економією місця і втратою селективності.
- Як прочитати `Sub_part=16` у `SHOW INDEX FROM …`.

### Задіяні таблиці

| Таблиця | Колонка |
|---|---|
| `idx_lab` | `sku` (перші 16 символів) |

### Завдання

1. `CREATE INDEX ix_prefix_sku ON idx_lab (sku(16));`.
2. Перевірте `SHOW INDEX FROM idx_lab` — `Sub_part = 16`.

### Очікуваний результат (реальний `SHOW INDEX`)

```text
+---------+------------+---------------+--------------+-------------+-----------+-------------+----------+--------+------+------------+
| Table   | Non_unique | Key_name      | Seq_in_index | Column_name | Collation | Cardinality | Sub_part | Packed | Null | Index_type |
+---------+------------+---------------+--------------+-------------+-----------+-------------+----------+--------+------+------------+
| idx_lab |          1 | ix_prefix_sku |            1 | sku         | A         |       39166 |       16 |   NULL |      | BTREE      |
+---------+------------+---------------+--------------+-------------+-----------+-------------+----------+--------+------+------------+
```

### Підказка

`Sub_part` — кількість байтів в індексі. `NULL` означає всю колонку.

### Розв'язання

```sql
CREATE INDEX ix_prefix_sku ON idx_lab (sku(16));

SHOW INDEX FROM idx_lab WHERE Key_name = 'ix_prefix_sku';

EXPLAIN
SELECT id FROM idx_lab WHERE sku LIKE 'SKU-000150%';

-- DROP INDEX ix_prefix_sku ON idx_lab;
```

### Покрокове пояснення

1. **`sku(16)`** індексує перші 16 байтів. У `utf8mb4` один символ — до 4 байтів; для ASCII-SKU це буквально перші 16 символів.
2. **Перевірка селективності:** якщо `LEFT(sku, 16)` уже стикається в багатьох рядках, префіксний індекс гірший за відсутність індекса. Обчисліть `SELECT COUNT(DISTINCT LEFT(sku, 16)) / COUNT(*) FROM idx_lab;` і прагніть до значення біля 1.
3. **Співіснування:** префіксний і повний індекси можуть жити поряд; оптимізатор обере дешевший для конкретного запиту. Тут ми лишили і `ix_uniq_sku`, і `ix_prefix_sku`.
4. **Навіщо це треба?** Повний індекс на `VARCHAR(80) utf8mb4` — це 322 байти на рядок. Префіксний — ~18 байт на рядок: у 18 разів менший, більше сторінок поміщається в RAM.

## Вправа 5 — FULLTEXT-індекс по `note`

### Контекст

Сервіс хоче шукати по полю `note` (там лежать назви запчастин) із рейтингом релевантності — користувач вводить слово, отримує знайдені рядки в порядку «найкраще збігається спочатку». Саме це робить `MATCH(note) AGAINST(...)` на FULLTEXT-індексі.

### Чого ви навчитеся

- Створити FULLTEXT-індекс через `ALTER TABLE … ADD FULLTEXT`.
- Синтаксис `MATCH(col) AGAINST('word')` (natural-language mode).
- Що FULLTEXT повертає **score релевантності** разом з рядками.

### Задіяні таблиці

| Таблиця | Колонка |
|---|---|
| `idx_lab` | `note` (`TEXT`) |

### Завдання

1. `ALTER TABLE idx_lab ADD FULLTEXT INDEX ix_ft_note (note);`.
2. Виконайте `MATCH(note) AGAINST('Part_15000')` і подивіться на `score`.

### Очікуваний результат (реальний вивід)

```text
+-------+--------------+-------------------+
| id    | sku          | score             |
+-------+--------------+-------------------+
| 15000 | SKU-00015000 | 21.16303825378418 |
+-------+--------------+-------------------+
```

`SHOW INDEX` підтверджує тип:

```text
+---------+------------+------------+--------------+-------------+------------+
| Table   | Non_unique | Key_name   | Seq_in_index | Column_name | Index_type |
+---------+------------+------------+--------------+-------------+------------+
| idx_lab |          1 | ix_ft_note |            1 | note        | FULLTEXT   |
+---------+------------+------------+--------------+-------------+------------+
```

### Підказка

Використовуйте той самий вираз у `SELECT` (для score) і в `WHERE` (для предиката).

### Розв'язання

```sql
ALTER TABLE idx_lab
  ADD FULLTEXT INDEX ix_ft_note (note);

SELECT id,
       sku,
       MATCH(note) AGAINST('Part_15000') AS score
FROM idx_lab
WHERE MATCH(note) AGAINST('Part_15000')
LIMIT 5;

-- Boolean mode: фрази, заперечення, префікси
-- SELECT id FROM idx_lab WHERE MATCH(note) AGAINST('+Part* -Brand' IN BOOLEAN MODE);

-- ALTER TABLE idx_lab DROP INDEX ix_ft_note;
```

### Покрокове пояснення

1. **Natural-language mode (за замовчуванням)** упорядковує рядки за `score`. Число `21.16…` — це TF-IDF-подібний показник; більше — кращий збіг.
2. **Стоп-слова та мінімальна довжина токена** можуть приховати результати. У InnoDB за замовчуванням мінімальна довжина — 3 символи; коротші ігноруються. Налаштовується через `innodb_ft_min_token_size`.
3. **Boolean mode** (`AGAINST('+word -bad' IN BOOLEAN MODE)`) підтримує `+` (мусить бути), `-` (не повинно бути), `*` (суфіксний шаблон), `"phrase"`.
4. **Де не варто:** точний лукап на кшталт `SKU-00015000` — для нього звичайний B-tree на `sku` буде швидшим і точнішим.
5. **`DROP`:** старі MySQL інколи не видаляють FULLTEXT через `DROP INDEX`; використовуйте `ALTER TABLE … DROP INDEX` як надійний варіант.

## Вправа 6 — Функціональний / виразовий індекс `(LOWER(sku))`

### Контекст

Пошук у каталозі case-insensitive: користувач вводить `sku-00015000`, у базі лежить `SKU-00015000`. Без індексу по **виразу** `LOWER(sku)` кожен запит мусить пройти всією таблицею і знизити регістр кожному рядку. Функціональний індекс заздалегідь зберігає знижене значення.

### Чого ви навчитеся

- `CREATE INDEX … ((expr))` (зверніть увагу на подвійні дужки — обов'язкові з MySQL 8.0.13).
- Оптимізатор підбирає **точний** вираз: `LOWER(sku)` у `WHERE` має співпадати з `(LOWER(sku))` в індексі.

### Задіяні таблиці

| Таблиця | Вираз |
|---|---|
| `idx_lab` | `LOWER(sku)` |

### Завдання

1. `CREATE INDEX ix_func_lower_sku ON idx_lab ((LOWER(sku)));`.
2. `EXPLAIN` case-insensitive рівність.

### Очікуваний результат (реальний `EXPLAIN`)

```text
+----+-------------+---------+------------+------+-------------------+-------------------+---------+-------+------+----------+-------+
| id | select_type | table   | partitions | type | possible_keys     | key               | key_len | ref   | rows | filtered | Extra |
+----+-------------+---------+------------+------+-------------------+-------------------+---------+-------+------+----------+-------+
|  1 | SIMPLE      | idx_lab | NULL       | ref  | ix_func_lower_sku | ix_func_lower_sku | 323     | const |    1 |   100.00 | NULL  |
+----+-------------+---------+------------+------+-------------------+-------------------+---------+-------+------+----------+-------+
```

Зразок рядка:

```text
+-------+--------------+
| id    | sku          |
+-------+--------------+
| 15000 | SKU-00015000 |
+-------+--------------+
```

### Підказка

`type=ref` + `key=ix_func_lower_sku` — те, що треба. Якщо оптимізатор лишився на `ALL`, вираз у `WHERE` не збігається посимвольно з виразом індексу.

### Розв'язання

```sql
CREATE INDEX ix_func_lower_sku ON idx_lab ((LOWER(sku)));

EXPLAIN
SELECT id FROM idx_lab WHERE LOWER(sku) = 'sku-00015000';

SELECT id, sku FROM idx_lab WHERE LOWER(sku) = 'sku-00015000';

-- DROP INDEX ix_func_lower_sku ON idx_lab;
```

### Покрокове пояснення

1. **Подвійні дужки обов'язкові.** `CREATE INDEX … (LOWER(sku))` — синтаксична помилка: MySQL парсить це як список колонок. Додаткові `(())` означають «це вираз».
2. **Вираз має збігатися точно.** `WHERE LOWER(sku) = …` бере індекс; `WHERE LOWER(sku || '')` — ні. Навіть різниця у згортанні констант може зруйнувати збіг.
3. **Альтернатива — generated columns.** На старих версіях MySQL еквівалент: додати `STORED` / `VIRTUAL` згенерований стовпець і проіндексувати його.
4. **Побічний ефект:** записи стають трохи повільнішими, бо MySQL мусить перерахувати lower-версію і зберегти в B-дерево.

## Вправа 7 — SPATIAL-індекс на `POINT`

### Контекст

Диспетчер доставки хоче знайти всі точки клієнтів у межах прямокутника на карті («все на захід від Львова і на північ від Києва»). Просторові операції MySQL працюють зі `SPATIAL` індексом на колонці `POINT` з SRID.

### Чого ви навчитеся

- Створити колонку `POINT NOT NULL SRID 4326` і `SPATIAL INDEX` поверх неї.
- Фільтрувати через `MBRContains(polygon, point)` для швидкої перевірки прямокутника.
- Читати план `range`, який повертає просторовий індекс.

### Задіяні таблиці

| Таблиця | Колонка |
|---|---|
| `idx_geo` | `g POINT NOT NULL SRID 4326` |

### Завдання

1. Створіть `idx_geo` зі SPATIAL-індексом на `g`.
2. Засійте з `idx_lab` (`l.id <= 500`).
3. Запустіть фільтр `MBRContains` і подивіться `EXPLAIN`.

### Очікуваний результат (реальний `EXPLAIN`)

```text
+----+-------------+---------+------------+-------+---------------+--------------+---------+------+------+----------+-------------+
| id | select_type | table   | partitions | type  | possible_keys | key          | key_len | ref  | rows | filtered | Extra       |
+----+-------------+---------+------------+-------+---------------+--------------+---------+------+------+----------+-------------+
|  1 | SIMPLE      | idx_geo | NULL       | range | ix_spatial_g  | ix_spatial_g | 34      | NULL |  500 |   100.00 | Using where |
+----+-------------+---------+------------+-------+---------------+--------------+---------+------+------+----------+-------------+
```

Зразок рядків:

```text
+-----+-------------------+
| id  | point             |
+-----+-------------------+
| 399 | POINT(-0.2 49.75) |
| 199 | POINT(-0.2 49.75) |
| 439 | POINT(-2.2 49.75) |
+-----+-------------------+
```

### Підказка

`SPATIAL INDEX` працює лише на `NOT NULL` geometry-колонках; SRID треба зафіксувати в DDL колонки.

### Розв'язання

```sql
DROP TABLE IF EXISTS idx_geo;

CREATE TABLE idx_geo (
  id INT NOT NULL AUTO_INCREMENT,
  g  POINT NOT NULL SRID 4326,
  PRIMARY KEY (id),
  SPATIAL INDEX ix_spatial_g (g)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci;

INSERT INTO idx_geo (g)
SELECT ST_PointFromText(
         CONCAT('POINT(', -10 + (l.id MOD 50) / 5.0, ' ', 40 + (l.id MOD 40) / 4.0, ')'),
         4326
       )
FROM idx_lab AS l
WHERE l.id <= 500;

EXPLAIN
SELECT id FROM idx_geo
WHERE MBRContains(
        ST_GeomFromText('POLYGON((-20 35, 20 35, 20 55, -20 55, -20 35))', 4326),
        g
      );

SELECT id, ST_AsText(g) AS point
FROM idx_geo
WHERE MBRContains(
        ST_GeomFromText('POLYGON((-20 35, 20 35, 20 55, -20 55, -20 35))', 4326),
        g
      )
LIMIT 5;
```

### Покрокове пояснення

1. **`POINT NOT NULL SRID 4326`** оголошує колонку у WGS-84 (стандартний «GPS» SRID). SPATIAL-індекс потребує `NOT NULL`.
2. **`MBRContains(polygon, point)`** — це тест за обмежувальним прямокутником (minimum bounding rectangle). Індекс дає грубий збіг, далі MySQL перевіряє геометрію точно.
3. **`type=range` з `key=ix_spatial_g`** підтверджує, що просторовий індекс задіявся. SPATIAL-індекси — R-tree варіанти; `EXPLAIN` використовує ту саму мітку `range`.
4. **Пастка з SRID:** якщо у полігона і точок різний SRID, MySQL кидає `Cannot get geometry object …`. Завжди вказуйте `4326` явно в `ST_GeomFromText`.

## Очищення

Скрипт-компаньйон закінчується опційними `DROP TABLE` для лабораторних таблиць. Закоментуйте їх, якщо хочете й далі експериментувати. Імена індексів починаються з префіксу `ix_`, тож їх легко знайти у `SHOW INDEX FROM idx_lab`.

## Поради при дивній поведінці

| Симптом | Імовірне виправлення |
|---|---|
| `CREATE UNIQUE INDEX` фейлиться з `Duplicate entry …` | У даних є дублікати; почистіть або беріть звичайний `INDEX`. |
| `EXPLAIN` далі показує `type=ALL` після `CREATE INDEX` | Предикат не збігається з індексом (функція на колонці, неправильний тип, провідний `%` в `LIKE`). |
| Композитний індекс ігнорується | Відсутня ведуча колонка у `WHERE`, або оптимізатор вважає інший індекс дешевшим. Перевірте `FORCE INDEX (…)`. |
| `FULLTEXT` нічого не повертає | Слово коротше за `innodb_ft_min_token_size` або у стоп-листі. Спробуйте довше слово або boolean mode. |
| `SPATIAL` помилка `Cannot get geometry…` | Розбіжність SRID — завжди вказуйте `SRID 4326` (чи ваш SRID) і в колонці, і в запиті. |
| Індекс ніби не використовується | Запустіть `ANALYZE TABLE idx_lab;` для оновлення статистики. |
