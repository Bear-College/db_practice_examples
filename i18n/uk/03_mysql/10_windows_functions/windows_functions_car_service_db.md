# Віконні функції — `car_service_db`

> Translation / Переклад: [English](../../../../03_mysql/10_windows_functions/windows_functions_car_service_db.md)

Ці вправи проходять **віконні (аналітичні) функції** на справжній базі з **`01_database_mysql/car_service_db.sql.gz`** (ім'я бази: **`car_service_db`**). Віконна функція обчислює значення для **кожного вхідного рядка**, дивлячись на «вікно» сусідніх рядків — на відміну від `GROUP BY`, рядки **не згортаються**.

```bash
mysql -u root -e "CREATE DATABASE IF NOT EXISTS car_service_db;"
gunzip -c 01_database_mysql/car_service_db.sql.gz | mysql -u root car_service_db
mysql -u root car_service_db < 03_mysql/10_windows_functions/car_service_windows_functions_examples.sql
```

**Продуктивність:** дамп великий (~100 тис. рядків у кожній основній таблиці). Скрипт використовує **`WHERE id BETWEEN …`**, щоб запити лишалися швидкими на занятті.

## Анатомія віконної функції

```text
function(...) OVER ( [PARTITION BY ...] [ORDER BY ...] [frame] )
              ^^^^^   ^^^^^^^^^^^^^^^^^   ^^^^^^^^^^^^   ^^^^^
              ключове  «кошики», що       порядок для     які сусідні рядки
              слово    лишають рядки      ранжування /    подаються у функцію
                       видимими           зсувів (LAG…)   (ROWS / RANGE)
```

| Секція | Роль |
|---|---|
| **`OVER ( )`** | Перетворює агрегат або ранкінг-функцію на **віконну** (рядок лишається видимим). |
| **`PARTITION BY`** | Окремі вікна для груп (як `GROUP BY`, але без згортання рядків). |
| **`ORDER BY` всередині `OVER`** | Порядок рядків **усередині** партиції (потрібен для ранкінгу, `LAG`/`LEAD`, накопичувальних сум). |
| **Фрейм `ROWS` / `RANGE`** | Які сусідні рядки подаються у функцію (використовується в `LAST_VALUE`, ковзних агрегатах). |
| **`WINDOW name AS (…)`** | Перевикористати одне визначення вікна для кількох функцій. |

### Зауваження про `LAST_VALUE`

З **типовим фреймом** (`RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`) **`LAST_VALUE()`** повертає значення **поточного** рядка, а не останнього у партиції. Щоб отримати справді «останній у партиції», задайте явний фрейм `ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING` (див. Вправу W7).

## Вправа W1 — `ROW_NUMBER()` (унікальна послідовність у партиції)

### Контекст

Диспетчер хоче надрукувати «топ-5 найдорожчих відкритих робіт» для кожного статусу пайплайну (по одній секції на статус). Щоб точно взяти топ-5 у кожному кошику, потрібен **щільний унікальний порядковий номер у межах статусу** — саме це й дає `ROW_NUMBER()`.

### Чого ви навчитеся

- Як `ROW_NUMBER() OVER (PARTITION BY … ORDER BY …)` нумерує рядки **всередині** кожної партиції.
- Чому віконна функція дозволяє залишити окремі рядки видимими (на відміну від `GROUP BY`, який їх згортає).
- Що `ORDER BY` **всередині** `OVER` не пов'язаний з зовнішнім `ORDER BY` над результатом.

### Задіяні таблиці

| Таблиця | Колонки |
|---|---|
| `work_orders` | `id`, `status`, `total_cost` |

### Завдання

Для `work_orders` з `id BETWEEN 1 AND 5000` обчислити послідовність `rn_in_status` у межах кожного статусу. Сортувати партицію за `total_cost DESC`, далі за `id` для стабільності. Обмежити 40 рядків.

### Очікуваний результат

```text
+------+-----------+------------+--------------+
| id   | status    | total_cost | rn_in_status |
+------+-----------+------------+--------------+
| 5000 | cancelled |    1000.00 |            1 |
| 4995 | cancelled |     999.50 |            2 |
| 4990 | cancelled |     999.00 |            3 |
| 4985 | cancelled |     998.50 |            4 |
| 4980 | cancelled |     998.00 |            5 |
| 4975 | cancelled |     997.50 |            6 |
| 4970 | cancelled |     997.00 |            7 |
| 4965 | cancelled |     996.50 |            8 |
| 4960 | cancelled |     996.00 |            9 |
| 4955 | cancelled |     995.50 |           10 |
| 4950 | cancelled |     995.00 |           11 |
| 4945 | cancelled |     994.50 |           12 |
+------+-----------+------------+--------------+
```

### Підказка

Використати `ROW_NUMBER() OVER (PARTITION BY status ORDER BY total_cost DESC, id)` і назвати її `rn_in_status`.

### Розв'язання

```sql
SELECT id,
       status,
       total_cost,
       ROW_NUMBER() OVER (
         PARTITION BY status
         ORDER BY total_cost DESC, id
       ) AS rn_in_status
FROM work_orders
WHERE id BETWEEN 1 AND 5000
LIMIT 40;
```

### Покрокове пояснення

1. **`PARTITION BY status`** відкриває окреме вікно для кожного значення `status`. У кожному вікні нумерація стартує з `1`.
2. **`ORDER BY total_cost DESC, id`** всередині `OVER` визначає **порядок** у вікні — найдорожче замовлення у статусі отримує `rn_in_status = 1`. Друга колонка-розрив рівних робить порядок детермінованим.
3. **`ROW_NUMBER()`** — ранкінг-функція: **ніколи** не повторюється, навіть на однакових `total_cost`. Якщо потрібні «спільні» ранги для рівних — використовуйте `RANK` / `DENSE_RANK` (Вправа W2).
4. **Зовнішній `LIMIT 40` не залежить від вікна.** Вікно обчислюється для всього фільтрованого набору, потім `LIMIT` відрізає перші 40 рядків у фізичному порядку, який обере оптимізатор. Якщо хочете побачити конкретний статус першим — додайте зовнішній `ORDER BY`.

## Вправа W2 — `RANK()` проти `DENSE_RANK()`

### Контекст

У межах історії робіт кожного механіка старший майстер хоче побачити найдорожчі виконані роботи. Якщо дві роботи коштують однаково — обидві мають отримати однаковий ранг, але як далі: `1, 1, 3` чи `1, 1, 2`? `RANK` робить перше, `DENSE_RANK` — друге.

### Чого ви навчитеся

- Як `RANK()` обробляє ровесників (однаковий ранг, потім пропуск).
- Як `DENSE_RANK()` обробляє ровесників (однаковий ранг без пропусків).
- Що, попри ідентичний синтаксис із `ROW_NUMBER()`, семантика на ровесниках сильно інша.

### Задіяні таблиці

| Таблиця | Колонки |
|---|---|
| `work_orders` | `id`, `assigned_mechanic_id`, `total_cost` |

### Завдання

Для `work_orders` з `id BETWEEN 1 AND 8000` та `assigned_mechanic_id IS NOT NULL` повернути `RANK()` і `DENSE_RANK()` за `total_cost DESC` у межах кожного механіка. Обмежити 35 рядків.

### Очікуваний результат

```text
+----+----------------------+------------+-----+-----------+
| id | assigned_mechanic_id | total_cost | rnk | dense_rnk |
+----+----------------------+------------+-----+-----------+
|  1 |                    1 |     500.10 |   1 |         1 |
|  2 |                    2 |     500.20 |   1 |         1 |
|  3 |                    3 |     500.30 |   1 |         1 |
|  4 |                    4 |     500.40 |   1 |         1 |
|  5 |                    5 |     500.50 |   1 |         1 |
|  6 |                    6 |     500.60 |   1 |         1 |
|  7 |                    7 |     500.70 |   1 |         1 |
|  8 |                    8 |     500.80 |   1 |         1 |
|  9 |                    9 |     500.90 |   1 |         1 |
| 10 |                   10 |     501.00 |   1 |         1 |
| 11 |                   11 |     501.10 |   1 |         1 |
| 12 |                   12 |     501.20 |   1 |         1 |
+----+----------------------+------------+-----+-----------+
```

### Підказка

Дві віконні функції з **однаковим** `OVER (PARTITION BY assigned_mechanic_id ORDER BY total_cost DESC)`; назвати їх `rnk` і `dense_rnk`.

### Розв'язання

```sql
SELECT id,
       assigned_mechanic_id,
       total_cost,
       RANK() OVER (
         PARTITION BY assigned_mechanic_id
         ORDER BY total_cost DESC
       ) AS rnk,
       DENSE_RANK() OVER (
         PARTITION BY assigned_mechanic_id
         ORDER BY total_cost DESC
       ) AS dense_rnk
FROM work_orders
WHERE id BETWEEN 1 AND 8000
  AND assigned_mechanic_id IS NOT NULL
LIMIT 35;
```

### Покрокове пояснення

1. **`RANK()`** видає однаковий ранг ровесникам, після чого **пропускає** наступні значення так, щоб ранг відповідав фактичній позиції: `100, 100, 80` → `1, 1, 3`.
2. **`DENSE_RANK()`** теж ставить однаковий ранг ровесникам, але **без пропусків**: `100, 100, 80` → `1, 1, 2`. Беріть його, коли потрібен компактний номер «рівня» (наприклад, «рівень 1, рівень 2, рівень 3»).
3. **Зверніть увагу на цей дамп:** у `car_service_db` кожен `assigned_mechanic_id` зустрічається у `work_orders` рівно один раз, тому в кожній партиції лише один рядок — і обидві функції повертають `1` для кожного рядка. У реальному сервісі, де механік має десятки замовлень, дві функції розійдуться, щойно з'являться однакові `total_cost`.
4. **Обидві потребують `ORDER BY` всередині `OVER`.** Без нього база не знає, що таке «перший» і «другий» у партиції, і відхиляє запит.

## Вправа W3 — `SUM` / `AVG` як віконні агрегати

### Контекст

Для кожного замовлення менеджер хоче бачити вартість **та** підсумки по статусу, до якого воно належить (наприклад, «це замовлення на 500.10 з 1 999 500.00 загалом для `new`»). Додати підсумки як нові колонки — без втрати порядка деталей — це й роблять віконні агрегати.

### Чого ви навчитеся

- Агрегати (`SUM`, `AVG`, `MIN`, `MAX`, `COUNT`) стають **віконними**, якщо після них іде `OVER (...)`.
- Вони рахуються у межах партиції, але кожен вхідний рядок залишається видимим (на відміну від `GROUP BY`).
- Без `ORDER BY` усередині `OVER` вікно — **уся партиція** (без накопичення).

### Задіяні таблиці

| Таблиця | Колонки |
|---|---|
| `work_orders` | `id`, `status`, `total_cost` |

### Завдання

Для `work_orders` з `id BETWEEN 1 AND 10000` повернути `id`, `status`, `total_cost`, **суму** і **середнє** `total_cost` по всій партиції статусу. Обмежити 30.

### Очікуваний результат

```text
+-------+-----------+------------+--------------------+--------------------+
| id    | status    | total_cost | sum_cost_in_status | avg_cost_in_status |
+-------+-----------+------------+--------------------+--------------------+
|  9485 | cancelled |    1448.50 |         2000500.00 |        1000.250000 |
| 10000 | cancelled |    1500.00 |         2000500.00 |        1000.250000 |
|  9995 | cancelled |    1499.50 |         2000500.00 |        1000.250000 |
|  9990 | cancelled |    1499.00 |         2000500.00 |        1000.250000 |
|  9985 | cancelled |    1498.50 |         2000500.00 |        1000.250000 |
|  8715 | cancelled |    1371.50 |         2000500.00 |        1000.250000 |
|  9980 | cancelled |    1498.00 |         2000500.00 |        1000.250000 |
|  9975 | cancelled |    1497.50 |         2000500.00 |        1000.250000 |
|  9970 | cancelled |    1497.00 |         2000500.00 |        1000.250000 |
|  9965 | cancelled |    1496.50 |         2000500.00 |        1000.250000 |
+-------+-----------+------------+--------------------+--------------------+
```

### Підказка

`SUM(total_cost) OVER (PARTITION BY status)` і `AVG(total_cost) OVER (PARTITION BY status)`.

### Розв'язання

```sql
SELECT id,
       status,
       total_cost,
       SUM(total_cost) OVER (PARTITION BY status) AS sum_cost_in_status,
       AVG(total_cost) OVER (PARTITION BY status) AS avg_cost_in_status
FROM work_orders
WHERE id BETWEEN 1 AND 10000
LIMIT 30;
```

### Покрокове пояснення

1. **Кожен рядок зберігає свої деталі.** `id`, `status`, `total_cost` не змінюються; колонки вікна *додаються*.
2. **`PARTITION BY status` без `ORDER BY`** означає, що вікно — це **уся партиція**, тому `sum_cost_in_status` і `avg_cost_in_status` константні всередині партиції.
3. **Порівняйте з `GROUP BY status`:** там усі рядки статусу згорнулися б в один, і `id` / `total_cost` зникли б. Віконні агрегати і `GROUP BY` відповідають на різні запитання.
4. **Продуктивність:** база матеріалізує партицію один раз, потім «припилює» агрегат до кожного рядка. Це приблизно вартість self-join — але читабельніше.

## Вправа W4 — Накопичувальна сума (`SUM` з `ORDER BY` і фреймом `ROWS`)

### Контекст

Фінансовий відділ хоче побачити **накопичувальну суму** `total_cost` у межах статусу, у порядку `id`: для замовлення №N сума — це сума замовлень 1..N того ж статусу. Класична «cumulative» задача.

### Чого ви навчитеся

- Додавання `ORDER BY` всередині `OVER` змінює **типовий фрейм** на «рядки до поточного включно».
- Явний фрейм `ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW` робить намір прозорим.
- Накопичувальні суми пишуться декларативно через вікна — без жодного процедурного циклу.

### Задіяні таблиці

| Таблиця | Колонки |
|---|---|
| `work_orders` | `id`, `status`, `total_cost` |

### Завдання

Для `work_orders` з `id BETWEEN 1 AND 2000` обчислити `running_sum_same_status = SUM(total_cost)` по рядках **того ж статусу**, упорядкованих за `id`, від першого рядка партиції до поточного включно. Обмежити 25.

### Очікуваний результат

```text
+----+-----------+------------+-------------------------+
| id | status    | total_cost | running_sum_same_status |
+----+-----------+------------+-------------------------+
|  5 | cancelled |     500.50 |                  500.50 |
| 10 | cancelled |     501.00 |                 1001.50 |
| 15 | cancelled |     501.50 |                 1503.00 |
| 20 | cancelled |     502.00 |                 2005.00 |
| 25 | cancelled |     502.50 |                 2507.50 |
| 30 | cancelled |     503.00 |                 3010.50 |
| 35 | cancelled |     503.50 |                 3514.00 |
| 40 | cancelled |     504.00 |                 4018.00 |
| 45 | cancelled |     504.50 |                 4522.50 |
| 50 | cancelled |     505.00 |                 5027.50 |
| 55 | cancelled |     505.50 |                 5533.00 |
| 60 | cancelled |     506.00 |                 6039.00 |
+----+-----------+------------+-------------------------+
```

### Підказка

`SUM(total_cost) OVER (PARTITION BY status ORDER BY id ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)`.

### Розв'язання

```sql
SELECT id,
       status,
       total_cost,
       SUM(total_cost) OVER (
         PARTITION BY status
         ORDER BY id
         ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
       ) AS running_sum_same_status
FROM work_orders
WHERE id BETWEEN 1 AND 2000
LIMIT 25;
```

### Покрокове пояснення

1. **`ORDER BY id` всередині `OVER`** задає послідовність, у якій рядки накопичуються.
2. **Фрейм** `ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW` означає: «від першого рядка партиції до поточного». Замініть `UNBOUNDED PRECEDING` на `2 PRECEDING` — отримаєте **ковзну суму з 3 рядків**.
3. **`ROWS` vs `RANGE`:** `ROWS` рахує фізичні рядки; `RANGE` дивиться на діапазон значень ключа `ORDER BY`. На унікальних `id` поведінка однакова; при ровесниках `RANGE` включає всіх ровесників.
4. **Типова пастка:** додання `ORDER BY` у `OVER` *без* явного фрейму неявно дає `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW` — ви отримуєте накопичувальну суму, навіть якщо її не просили. Завжди задавайте фрейм явно, коли семантика важлива (див. W7).

## Вправа W5 — `LAG()` і `LEAD()` (попередній і наступний рядок)

### Контекст

Коли майстер переглядає день механіка, корисно бачити кожне замовлення поряд із **попереднім** і **наступним** `total_cost` — щоб помітити аномалії (різкий стрибок у 10×) або просто шаблони послідовності. `LAG` / `LEAD` дивляться назад / вперед у вікні без self-join.

### Чого ви навчитеся

- `LAG(col, n)` повертає `col` із рядка на `n` позицій **раніше** у вікні.
- `LEAD(col, n)` повертає `col` із рядка на `n` позицій **пізніше**.
- На межі повертається `NULL` (або явний default, якщо передати третій аргумент).

### Задіяні таблиці

| Таблиця | Колонки |
|---|---|
| `work_orders` | `id`, `assigned_mechanic_id`, `total_cost` |

### Завдання

Для `work_orders` з `id BETWEEN 1 AND 12000` та `assigned_mechanic_id IS NOT NULL` повернути `prev_cost = LAG(total_cost, 1)` та `next_cost = LEAD(total_cost, 1)` у порядку `id` для кожного механіка. Обмежити 35.

### Очікуваний результат

```text
+----+----------------------+------------+-----------+-----------+
| id | assigned_mechanic_id | total_cost | prev_cost | next_cost |
+----+----------------------+------------+-----------+-----------+
|  1 |                    1 |     500.10 |      NULL |      NULL |
|  2 |                    2 |     500.20 |      NULL |      NULL |
|  3 |                    3 |     500.30 |      NULL |      NULL |
|  4 |                    4 |     500.40 |      NULL |      NULL |
|  5 |                    5 |     500.50 |      NULL |      NULL |
|  6 |                    6 |     500.60 |      NULL |      NULL |
|  7 |                    7 |     500.70 |      NULL |      NULL |
|  8 |                    8 |     500.80 |      NULL |      NULL |
|  9 |                    9 |     500.90 |      NULL |      NULL |
| 10 |                   10 |     501.00 |      NULL |      NULL |
+----+----------------------+------------+-----------+-----------+
```

### Підказка

Обидві функції приймають `(колонка, зсув)`; необов'язковий третій аргумент — значення за замовчуванням, коли зсув виходить за межі вікна.

### Розв'язання

```sql
SELECT id,
       assigned_mechanic_id,
       total_cost,
       LAG(total_cost, 1) OVER (
         PARTITION BY assigned_mechanic_id
         ORDER BY id
       ) AS prev_cost,
       LEAD(total_cost, 1) OVER (
         PARTITION BY assigned_mechanic_id
         ORDER BY id
       ) AS next_cost
FROM work_orders
WHERE id BETWEEN 1 AND 12000
  AND assigned_mechanic_id IS NOT NULL
LIMIT 35;
```

### Покрокове пояснення

1. **`LAG(total_cost, 1)`** повертає `total_cost` попереднього рядка у тій самій партиції `assigned_mechanic_id`. У першого рядка партиції попередника немає — звідси `NULL`.
2. **`LEAD(total_cost, 1)`** симетричний: «наступний» останнього рядка — `NULL`.
3. **Про цей дамп:** кожен `assigned_mechanic_id` має лише одне замовлення, тому всі партиції розміру 1 — кожен рядок одночасно перший і останній, і `prev_cost` / `next_cost` завжди `NULL`. Щоб побачити живі значення, партиціонуйте по чомусь з повтореннями (наприклад, `PARTITION BY status`) або використовуйте базу, де механіки мають кілька замовлень.
4. **Значення за замовчуванням:** `LAG(total_cost, 1, 0)` повертатиме `0` замість `NULL` на межі — корисно, коли результат іде в арифметику, що не толерує `NULL`.

## Вправа W6 — `NTILE(n)` (розбиття партиції на «кошики»)

### Контекст

Команда ціноутворення хоче розбити замовлення в кожному статусі на **чотири квартилі за вартістю**, щоб окремо аналізувати «дорогі 25%» та «дешеві 25%». `NTILE(4)` робить це однією віконною функцією.

### Чого ви навчитеся

- `NTILE(n)` ділить кожну партицію на `n` приблизно рівних кошиків.
- Номери кошиків — від `1` до `n`; якщо розмір партиції не ділиться на `n`, додаткові рядки потрапляють у перші кошики.
- У комбінації з `PARTITION BY` отримуєте квартилі для кожної групи за один прохід.

### Задіяні таблиці

| Таблиця | Колонки |
|---|---|
| `work_orders` | `id`, `status`, `total_cost` |

### Завдання

Для `work_orders` з `id BETWEEN 1 AND 8000` партиціонувати за `status`, сортувати у партиції за `total_cost DESC, id` і позначити кожен рядок номером кошика `NTILE(4)` (так, щоб кошик `1` — найдорожча чверть кожного статусу). Обмежити 32.

### Очікуваний результат

```text
+------+-----------+------------+-----------------+
| id   | status    | total_cost | quartile_bucket |
+------+-----------+------------+-----------------+
| 8000 | cancelled |    1300.00 |               1 |
| 7995 | cancelled |    1299.50 |               1 |
| 7990 | cancelled |    1299.00 |               1 |
| 7985 | cancelled |    1298.50 |               1 |
| 7980 | cancelled |    1298.00 |               1 |
| 7975 | cancelled |    1297.50 |               1 |
| 7970 | cancelled |    1297.00 |               1 |
| 7965 | cancelled |    1296.50 |               1 |
| 7960 | cancelled |    1296.00 |               1 |
| 7955 | cancelled |    1295.50 |               1 |
| 7950 | cancelled |    1295.00 |               1 |
| 7945 | cancelled |    1294.50 |               1 |
+------+-----------+------------+-----------------+
```

### Підказка

`NTILE(4) OVER (PARTITION BY status ORDER BY total_cost DESC, id)`.

### Розв'язання

```sql
SELECT id,
       status,
       total_cost,
       NTILE(4) OVER (
         PARTITION BY status
         ORDER BY total_cost DESC, id
       ) AS quartile_bucket
FROM work_orders
WHERE id BETWEEN 1 AND 8000
LIMIT 32;
```

### Покрокове пояснення

1. **`NTILE(4)`** нумерує рядки 1..4 у кожній партиції. Порядок важливий: `ORDER BY total_cost DESC` означає, що квартиль `1` — найдорожчий.
2. **Нерівні поділи:** партиція з 10 рядків ділиться на 4 кошики як `3, 3, 2, 2` — «зайві» рядки потрапляють у **менші номери** кошиків.
3. **Видимий верхній зріз:** у виводі показано лише квартиль `1`, бо `LIMIT 32` обрізає до другого квартиля. Зніміть `LIMIT` (або відсортуйте за кошиком), щоб побачити всі чотири.
4. **Увага:** `NTILE` вимагає `ORDER BY` всередині `OVER`; без нього розподіл по кошиках був би недетермінованим, і MySQL відмовляється виконувати запит.

## Вправа W7 — `FIRST_VALUE` і `LAST_VALUE` (явний фрейм)

### Контекст

Для кожного авто історія сервісу хоче показати **перше** і **останнє** значення `total_cost` — корисно для запитання «як це авто розвивалося від першого візиту до останнього?». Потрібен правильний **фрейм** вікна, бо `LAST_VALUE` із типовим фреймом — відома пастка.

### Чого ви навчитеся

- `FIRST_VALUE(col)` повертає `col` із першого рядка фрейму.
- `LAST_VALUE(col)` повертає `col` із **останнього** рядка фрейму — який за замовчуванням **не** збігається з останнім рядком партиції.
- Виправлення: `ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING` робить фрейм усією партицією.

### Задіяні таблиці

| Таблиця | Колонки |
|---|---|
| `work_orders` | `id`, `vehicle_id`, `total_cost` |

### Завдання

Для `work_orders` з `id BETWEEN 1 AND 6000` для кожної партиції `vehicle_id` повернути перший і останній `total_cost` (у порядку `id`) із **явним фреймом `ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING`**. Обмежити 30.

### Очікуваний результат

```text
+----+------------+------------+---------------------------+--------------------------+
| id | vehicle_id | total_cost | first_wo_cost_for_vehicle | last_wo_cost_for_vehicle |
+----+------------+------------+---------------------------+--------------------------+
|  1 |          1 |     500.10 |                    500.10 |                   500.10 |
|  2 |          2 |     500.20 |                    500.20 |                   500.20 |
|  3 |          3 |     500.30 |                    500.30 |                   500.30 |
|  4 |          4 |     500.40 |                    500.40 |                   500.40 |
|  5 |          5 |     500.50 |                    500.50 |                   500.50 |
|  6 |          6 |     500.60 |                    500.60 |                   500.60 |
|  7 |          7 |     500.70 |                    500.70 |                   500.70 |
|  8 |          8 |     500.80 |                    500.80 |                   500.80 |
|  9 |          9 |     500.90 |                    500.90 |                   500.90 |
| 10 |         10 |     501.00 |                    501.00 |                   501.00 |
+----+------------+------------+---------------------------+--------------------------+
```

### Підказка

Задайте явний фрейм `ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING` **для обох** функцій — `FIRST_VALUE` і `LAST_VALUE`.

### Розв'язання

```sql
SELECT id,
       vehicle_id,
       total_cost,
       FIRST_VALUE(total_cost) OVER (
         PARTITION BY vehicle_id
         ORDER BY id
         ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING
       ) AS first_wo_cost_for_vehicle,
       LAST_VALUE(total_cost) OVER (
         PARTITION BY vehicle_id
         ORDER BY id
         ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING
       ) AS last_wo_cost_for_vehicle
FROM work_orders
WHERE id BETWEEN 1 AND 6000
LIMIT 30;
```

### Покрокове пояснення

1. **Пастка типового фрейму.** Коли у `OVER` є `ORDER BY` і **немає фрейму**, MySQL ставить `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`. `LAST_VALUE` тоді повертає **поточний** рядок, а не останній у партиції.
2. **Виправлення:** розширюємо фрейм до всієї партиції через `ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING`. Тепер `LAST_VALUE` справді дивиться на останній рядок.
3. **`FIRST_VALUE` безпечніший** (типовий фрейм уже включає перший рядок), але писати однаковий явний фрейм для обох — це симетрично і читабельно.
4. **Про цей дамп:** кожен `vehicle_id` у `id BETWEEN 1 AND 6000` має лише одне замовлення, тому перше і останнє — це той самий рядок. Вивід ілюструє синтаксис — перезапустіть на авто з кількома замовленнями, щоб побачити різні перше/останнє.

## Вправа W8 — Іменоване вікно `WINDOW` (DRY для кількох функцій)

### Контекст

Коли потрібно кілька віконних функцій із **однаковими** партицією й порядком, повторювати `OVER (...)` шумно і небезпечно. Секція `WINDOW` дозволяє назвати вікно один раз і використати скрізь — як псевдонім для визначення вікна.

### Чого ви навчитеся

- Окрема секція `WINDOW name AS (...)` (після `WHERE`/`GROUP BY`/`HAVING`, перед `ORDER BY`).
- Посилання на іменоване вікно через `OVER w`.
- Що `PERCENT_RANK()` повертає значення в `[0, 1]` — відносну позицію.

### Задіяні таблиці

| Таблиця | Колонки |
|---|---|
| `work_orders` | `id`, `status`, `total_cost` |

### Завдання

Для `work_orders` з `id BETWEEN 1 AND 4000` визначити іменоване вікно `w` = `PARTITION BY status ORDER BY total_cost DESC, id`, потім обчислити `ROW_NUMBER() OVER w` та `PERCENT_RANK() OVER w`. Обмежити 30.

### Очікуваний результат

```text
+------+-----------+------------+----+-----------------------+
| id   | status    | total_cost | rn | pr                    |
+------+-----------+------------+----+-----------------------+
| 4000 | cancelled |     900.00 |  1 |                     0 |
| 3995 | cancelled |     899.50 |  2 | 0.0012515644555694619 |
| 3990 | cancelled |     899.00 |  3 | 0.0025031289111389237 |
| 3985 | cancelled |     898.50 |  4 | 0.0037546933667083854 |
| 3980 | cancelled |     898.00 |  5 | 0.0050062578222778474 |
| 3975 | cancelled |     897.50 |  6 |  0.006257822277847309 |
| 3970 | cancelled |     897.00 |  7 |  0.007509386733416771 |
| 3965 | cancelled |     896.50 |  8 |  0.008760951188986232 |
| 3960 | cancelled |     896.00 |  9 |  0.010012515644555695 |
| 3955 | cancelled |     895.50 | 10 |  0.011264080100125156 |
| 3950 | cancelled |     895.00 | 11 |  0.012515644555694618 |
| 3945 | cancelled |     894.50 | 12 |   0.01376720901126408 |
+------+-----------+------------+----+-----------------------+
```

### Підказка

Поставте `WINDOW w AS (PARTITION BY status ORDER BY total_cost DESC, id)` один раз на рівні запиту, а далі пишіть `OVER w` замість повторення дужок.

### Розв'язання

```sql
SELECT id,
       status,
       total_cost,
       ROW_NUMBER()    OVER w AS rn,
       PERCENT_RANK()  OVER w AS pr
FROM work_orders
WHERE id BETWEEN 1 AND 4000
WINDOW w AS (PARTITION BY status ORDER BY total_cost DESC, id)
LIMIT 30;
```

### Покрокове пояснення

1. **`WINDOW w AS (...)`** оголошує ім'я вікна `w` один раз. Тіло — точно те, що було б усередині `OVER (...)`.
2. **`OVER w`** посилається на іменоване вікно. Кілька функцій на одному вікні читаються консистентно і не розходяться — змініть `ORDER BY` у визначенні, і всі функції підлаштуються.
3. **`PERCENT_RANK()`** повертає `(rank − 1) / (rows − 1)`. Перший рядок партиції завжди `0`; останній — завжди `1`. У виводі перший рядок `0`, другий — `≈ 0.00125`, що відповідає ~800 рядкам на статус у цьому зрізі.
4. **Порядок секцій важливий:** `WINDOW` ставиться **після** `HAVING` і **перед** `ORDER BY`. Інакше — синтаксична помилка.

## Розв'язання проблем

| Симптом | Що зробити |
|---|---|
| `Window function 'ROW_NUMBER' is not allowed here` | Віконні функції дозволені лише у `SELECT` і `ORDER BY`. Загорніть запит у підзапит / CTE, якщо потрібен фільтр по рангу. |
| `LAST_VALUE` дорівнює поточному рядку | Це пастка типового фрейму. Додайте `ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING` (див. W7). |
| `RANK` і `DENSE_RANK` дають однаковий вивід | Немає ровесників за ключем `ORDER BY` — функції розходяться лише на ровесниках. |
| `LAG` / `LEAD` повертають лише `NULL` | У кожній партиції лише один рядок або зсув перевищує її розмір — перевірте `COUNT(*)` на партицію. |
| MySQL 5.7 відхиляє синтаксис | Віконні функції потребують MySQL **8.0+**. |

Щоб запустити **всі** приклади одразу: `mysql -t -u root car_service_db < 03_mysql/10_windows_functions/car_service_windows_functions_examples.sql`.
