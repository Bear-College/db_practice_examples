**Виконуйте скрипт в одній клієнтській сесії**, щоб `@`-змінні зберігалися між операторами. Кожне нове з'єднання `mysql` стартує з порожньою таблицею змінних.

## Швидкий довідник

| Поняття | Нотатки |
|---|---|
| **`SET @x = expr`**, **`SET @x := expr`** | Обидва працюють у `SET`. Тут `=` і `:=` рівнозначні. |
| **`SET @a = 1, @b = 2`** | Кілька присвоєнь в одному операторі. |
| **`SELECT @x := col FROM …`** | Присвоєння **всередині** запиту; значення можна прочитати і записати в один прохід рядків. |
| **Тип** | Без типу — `@x` «підстроюється» під те, що зберігаєте (`INT`, `DECIMAL`, рядок, `NULL`). |
| **Область видимості** | На рівні сесії; зникає при закритті з'єднання (або після `SET @x := NULL`). |
| **Системні змінні** | `@@version`, `@@session.x`, `@@global.x`. Читаються через `SELECT @@…` або `SHOW VARIABLES LIKE 'x'`. |
| **Не те саме, що `DECLARE`** | Локальні змінні всередині збережених програм (`DECLARE ім'я ТИП`) — інша область видимості, тут не розглядається. |

Поширене відкриття: **користувацькі змінні і підготовлені запити поділяють сесію**. У `PREPARE` можна поставити `?` як плейсхолдер і прив'язати їх через `EXECUTE … USING @var, @var, …` (Вправи V3 і V6).

## Вправа V1 — `SET` діапазону і використання у `WHERE`

### Контекст

Нічний пакет вивантажує зріз свіжих замовлень у звіт CSV. Сьогоднішній зріз — `id` від 1 до 800. Якщо завтра діапазон зміниться, краще змінити межі **в одному місці** на початку скрипта, ніж шукати-замінювати по всьому тілу запиту.

### Чого ви навчитеся

- Оголошення користувацьких змінних через `SET @name := value`.
- Читання їх у будь-якому подальшому операторі тієї ж сесії.
- Чому винесення «магічних чисел» на початок скрипта робить його самодокументованим.

### Задіяні таблиці

| Таблиця | Колонки |
|---|---|
| `work_orders` | `id`, `status`, `total_cost` |

### Завдання

Призначте дві користувацькі змінні `@wo_lo := 1` і `@wo_hi := 800`. Потім поверніть `id`, `status`, `total_cost` для `work_orders` з `id BETWEEN @wo_lo AND @wo_hi`, упорядковані за `id`, ліміт 15.

### Очікуваний результат

```text
+----+---------------+------------+
| id | status        | total_cost |
+----+---------------+------------+
|  1 | new           |     500.10 |
|  2 | in_progress   |     500.20 |
|  3 | waiting_parts |     500.30 |
|  4 | completed     |     500.40 |
|  5 | cancelled     |     500.50 |
|  6 | new           |     500.60 |
|  7 | in_progress   |     500.70 |
|  8 | waiting_parts |     500.80 |
|  9 | completed     |     500.90 |
| 10 | cancelled     |     501.00 |
| 11 | new           |     501.10 |
| 12 | in_progress   |     501.20 |
| 13 | waiting_parts |     501.30 |
| 14 | completed     |     501.40 |
| 15 | cancelled     |     501.50 |
+----+---------------+------------+
```

### Підказка

`SET @wo_lo := 1; SET @wo_hi := 800;` — потім використайте імена всередині `BETWEEN`.

### Розв'язання

```sql
SET @wo_lo := 1;
SET @wo_hi := 800;

SELECT id,
       status,
       total_cost
FROM work_orders
WHERE id BETWEEN @wo_lo AND @wo_hi
ORDER BY id
LIMIT 15;
```

### Покрокове пояснення

1. **`SET @wo_lo := 1`** створює змінну `@wo_lo` (якщо її ще немає) і присвоює ціле `1`. Префікс `@` відрізняє її від стовпця або псевдоніма.
2. **Змінні живуть у межах сесії.** Наступний оператор у тій же сесії їх бачить. Інше вікно `mysql`-клієнта — ні.
3. **`BETWEEN @wo_lo AND @wo_hi`** інтерпретується під час виконання; MySQL підставляє поточні значення. Змініть їх один раз — увесь скрипт підлаштується.
4. **Приведення типів:** `@wo_lo` зберігає «останнє записане значення». При порівнянні з колонкою `id INT` MySQL приводить за потреби. Зберігайте однаковий тип, щоб оптимізатору було легше.

## Вправа V2 — Присвоєння агрегату в змінну

### Контекст

Звітний запит обчислює «середній чек» один раз, потім використовує це число у двох наступних кроках (відсоток відхилення, прапорець «дорого»…). Перераховувати середнє щоразу — марнотратно і ризиковано. Збережіть його в користувацьку змінну і читайте звідусіль.

### Чого ви навчитеся

- Використання `:=` **всередині** `SELECT`, щоб захопити агрегат у момент його обчислення.
- Читання збереженого значення у наступних операторах.
- Час життя `@`-змінної між операторами тієї ж сесії.

### Задіяні таблиці

| Таблиця | Колонки |
|---|---|
| `work_orders` | `id`, `total_cost` |

### Завдання

Запустіть `SELECT … UNION ALL …`, який:

1. Обчислює `AVG(total_cost)` для `id BETWEEN 1 AND 50000` і зберігає в `@avg_cost`, повертаючи значення з міткою `'avg_total_cost'`.
2. Також повертає кількість рядків для того ж зрізу як `'rows_in_slice'`.

Потім другий запит зчитує `@avg_cost` двічі (щоб довести, що значення збереглося).

### Очікуваний результат

```text
+----------------+--------------+
| metric         | value        |
+----------------+--------------+
| avg_total_cost |  2999.950000 |
| rows_in_slice  | 50000.000000 |
+----------------+--------------+
+----------------------------+-------------------------------------+
| metric                     | value                               |
+----------------------------+-------------------------------------+
| stored_avg_total_cost      | 2999.950000000000000000000000000000 |
| stored_avg_total_cost_copy | 2999.950000000000000000000000000000 |
+----------------------------+-------------------------------------+
```

### Підказка

`@avg_cost := AVG(total_cost)` всередині `SELECT` одночасно обчислює **і** зберігає. Другий запит лише читає `@avg_cost`.

### Розв'язання

```sql
SELECT 'avg_total_cost' AS metric, @avg_cost := AVG(total_cost) AS value
FROM work_orders
WHERE id BETWEEN 1 AND 50000
UNION ALL
SELECT 'rows_in_slice' AS metric, COUNT(*) AS value
FROM work_orders
WHERE id BETWEEN 1 AND 50000;

SELECT 'stored_avg_total_cost'      AS metric, @avg_cost AS value
UNION ALL
SELECT 'stored_avg_total_cost_copy' AS metric, @avg_cost AS value;
```

### Покрокове пояснення

1. **`@avg_cost := AVG(total_cost)`** виконує подвійну роботу: повертає середнє як стовпець результату **і** записує його в сесійну змінну.
2. **Два блоки виводу** — скрипт містить два окремі запити, тому клієнт `mysql` друкує дві таблиці. Друга доводить, що змінна збереглася.
3. **Слідкуйте за точністю.** Усередині агрегату `value` — `DECIMAL`, друкована ширина невелика. Після збереження `@avg_cost` тримається з додатковою точністю (`2999.95000…0000`) — MySQL зберігає користувацькі змінні з **великою точністю**. Загорніть у `ROUND(@avg_cost, 2)` для охайного виводу.
4. **Порядок обчислень:** в одному `SELECT` MySQL не гарантує зліва-направо. Не покладайтеся на `@a := x, @b := @a + 1` — користуйтеся окремими операторами або трюками з `LEAST/GREATEST`.

## Вправа V3 — Пагінація через змінні і `PREPARE` / `EXECUTE`

### Контекст

У вебзастосунку є пагінований список замовлень (по 12 на сторінку). Номер сторінки приходить з URL. Скрипт має обчислити offset як `page × page_size` і передати обидва значення в `LIMIT` — але **`LIMIT` не приймає користувацькі змінні напряму**. Портативний обхід — **підготовлені запити**.

### Чого ви навчитеся

- Чому `LIMIT @offset, @count` заборонено в звичайному SQL.
- Як `PREPARE … FROM @sql` компілює параметризований запит.
- Як `EXECUTE stmt USING @v1, @v2` прив'язує значення до плейсхолдерів `?`.
- Прибиранню через `DEALLOCATE PREPARE`.

### Задіяні таблиці

| Таблиця | Колонки |
|---|---|
| `work_orders` | `id`, `assigned_mechanic_id`, `total_cost` |

### Завдання

Сторінка 2 розміром 12: обчислити `@offset_rows = (@page − 1) × @page_size`, потім виконати підготовлений `SELECT` із двома `?` для `LIMIT ?, ?` і прив'язати їх через `EXECUTE … USING @offset_rows, @page_size`. Фільтр — `id BETWEEN 1 AND 3000`, сортування за `id`.

### Очікуваний результат

```text
+----+----------------------+------------+
| id | assigned_mechanic_id | total_cost |
+----+----------------------+------------+
| 13 |                   13 |     501.30 |
| 14 |                   14 |     501.40 |
| 15 |                   15 |     501.50 |
| 16 |                   16 |     501.60 |
| 17 |                   17 |     501.70 |
| 18 |                   18 |     501.80 |
| 19 |                   19 |     501.90 |
| 20 |                   20 |     502.00 |
| 21 |                   21 |     502.10 |
| 22 |                   22 |     502.20 |
| 23 |                   23 |     502.30 |
| 24 |                   24 |     502.40 |
+----+----------------------+------------+
```

### Підказка

Зберіть текст `SELECT` (з `?`) у `@sql_page`, потім `PREPARE stmt_page FROM @sql_page` і `EXECUTE stmt_page USING @offset_rows, @page_size`.

### Розв'язання

```sql
SET @page_size   := 12;
SET @page        := 2;
SET @offset_rows := (@page - 1) * @page_size;

SET @sql_page := 'SELECT id, assigned_mechanic_id, total_cost
                  FROM work_orders
                  WHERE id BETWEEN 1 AND 3000
                  ORDER BY id
                  LIMIT ?, ?';

PREPARE stmt_page FROM @sql_page;
EXECUTE stmt_page USING @offset_rows, @page_size;
DEALLOCATE PREPARE stmt_page;
```

### Покрокове пояснення

1. **Заборонена пряма форма** — `LIMIT @offset_rows, @page_size`. MySQL парсить аргументи `LIMIT` на етапі компіляції і (до зовсім свіжих версій) відмовляється приймати там змінні.
2. **Зберіть текст SQL** у `@sql_page`. Два `?` позиційні і мають бути в тому порядку, в якому ви будете їх прив'язувати: спочатку offset, потім count.
3. **`PREPARE … FROM @sql_page`** один раз парсить і планує запит. **`EXECUTE … USING …`** підставляє значення.
4. **Завжди робіть `DEALLOCATE PREPARE`** в кінці — кожне з'єднання має кеш з назвами підготовлених запитів, і покинуті займають місце.
5. **Математика пагінації:** номери сторінок зазвичай від `1`, тому `offset = (page − 1) * page_size`. Забути `− 1` — класична off-by-one помилка.

## Вправа V4 — Лічильник рядків через `:=` (трюк до віконних функцій)

### Контекст

До появи `ROW_NUMBER()` у MySQL 8 лічильник присвоювали у користувацьку змінну і нарощували по одному рядку. Шаблон досі актуальний у середовищах MySQL 5.7 і яскраво ілюструє «присвоєння всередині `SELECT`».

### Чого ви навчитеся

- Ініціалізація лічильника через `CROSS JOIN (SELECT @rn := 0) AS init`.
- Інкремент у проекції: `@rn := @rn + 1 AS row_seq`.
- Чому шаблон вимагає певного порядку обчислень — і де пастки.

### Задіяні таблиці

| Таблиця | Колонки |
|---|---|
| `work_orders` | `id`, `total_cost` |

### Завдання

Для `work_orders` з `id BETWEEN 1 AND 500`, упорядкованих за `id`, повернути `id`, `total_cost` і послідовність `row_seq` від `1`. Обмежити 20.

### Очікуваний результат

```text
+----+------------+---------+
| id | total_cost | row_seq |
+----+------------+---------+
|  1 |     500.10 |       1 |
|  2 |     500.20 |       2 |
|  3 |     500.30 |       3 |
|  4 |     500.40 |       4 |
|  5 |     500.50 |       5 |
|  6 |     500.60 |       6 |
|  7 |     500.70 |       7 |
|  8 |     500.80 |       8 |
|  9 |     500.90 |       9 |
| 10 |     501.00 |      10 |
| 11 |     501.10 |      11 |
| 12 |     501.20 |      12 |
| 13 |     501.30 |      13 |
| 14 |     501.40 |      14 |
| 15 |     501.50 |      15 |
| 16 |     501.60 |      16 |
| 17 |     501.70 |      17 |
| 18 |     501.80 |      18 |
| 19 |     501.90 |      19 |
| 20 |     502.00 |      20 |
+----+------------+---------+
```

### Підказка

`CROSS JOIN (SELECT @rn := 0) AS init` скидає змінну в `0` один раз **до** основного скану; потім `@rn := @rn + 1` інкрементує на кожному рядку.

### Розв'язання

```sql
SELECT id,
       total_cost,
       @rn := @rn + 1 AS row_seq
FROM work_orders
CROSS JOIN (SELECT @rn := 0) AS init
WHERE id BETWEEN 1 AND 500
ORDER BY id
LIMIT 20;
```

### Покрокове пояснення

1. **Ініціалізація у похідній таблиці.** `(SELECT @rn := 0) AS init` виконується один раз, повертає один рядок, який скидає `@rn`. `CROSS JOIN` приєднує її до основного запиту без впливу на кардинальність.
2. **Інкремент у `SELECT`.** Кожен рядок обчислює `@rn := @rn + 1` і повертає нове значення як `row_seq`.
3. **Порядок важливий.** `ORDER BY id` потрібен, щоб лічильник збігався з `id`. Без нього MySQL міг би пройти рядки у порядку зберігання, і ваша послідовність переплуталася б.
4. **Сучасна альтернатива:** `ROW_NUMBER() OVER (ORDER BY id)` (див. `10_windows_functions`). Чистіша, не залежить від порядку обчислень і працює після `GROUP BY`. Шукайте трюк зі змінними лише коли застрягли на MySQL 5.7.
5. **Попередження про депрекацію:** з MySQL 8.0, використання `:=` всередині `SELECT` для одночасного читання-запису однієї змінної у непростих виразах дає попередження. Плануйте міграцію на віконні функції.

## Вправа V5 — Кілька присвоєнь в одному `SET` і їх використання

### Контекст

Часто треба задати **парні межі** (low/high, min/max) в одному місці. У MySQL `SET` приймає список через кому, тому не треба двох операторів для `@lo` і `@hi`.

### Чого ви навчитеся

- `SET` через кому для пов'язаних змінних.
- Виклик заданих меж у запиті з `GROUP BY`.
- Використання `MOD(id, 2)` для розбиття на парні / непарні.

### Задіяні таблиці

| Таблиця | Колонки |
|---|---|
| `customers` | `id` |

### Завдання

Призначити `@cust_lo := 1, @cust_hi := 200` **одним** `SET`. Потім порахувати клієнтів з `id BETWEEN @cust_lo AND @cust_hi`, групуючи за `MOD(id, 2)` (бакет парності).

### Очікуваний результат

```text
+---------------+----------------------+
| parity_bucket | n_customers_in_range |
+---------------+----------------------+
|             1 |                  100 |
|             0 |                  100 |
+---------------+----------------------+
```

### Підказка

`SET @cust_lo := 1, @cust_hi := 200;` — між присвоєннями кома, **а не** крапка з комою.

### Розв'язання

```sql
SET @cust_lo := 1, @cust_hi := 200;

SELECT MOD(id, 2) AS parity_bucket,
       COUNT(*)   AS n_customers_in_range
FROM customers
WHERE id BETWEEN @cust_lo AND @cust_hi
GROUP BY MOD(id, 2);
```

### Покрокове пояснення

1. **Один `SET` із двома присвоєннями.** Еквівалент двох окремих `SET`, але групує межі для читабельності.
2. **`MOD(id, 2)`** повертає `0` для парних, `1` для непарних. Корисно для парності, демо шардингу і швидкої перевірки «балансу» вибірки.
3. **`GROUP BY MOD(id, 2)`** згортає кожен бакет; `COUNT(*)` повертає його розмір. Для `id BETWEEN 1 AND 200` очікуємо рівно 100 парних і 100 непарних.
4. **Чому без `ORDER BY`?** Два рядки — сортувати немає сенсу. Для дашбордів додайте явний `ORDER BY parity_bucket`, щоб макет звіту був стабільним.

## Вправа V6 — Загальний `PREPARE` / `EXECUTE` із трьома плейсхолдерами

### Контекст

Той самий протокол підготовлених запитів, що у V3, але з трьома плейсхолдерами — для діапазону `BETWEEN` і `LIMIT`. Це повсякденна форма «параметричного звіту».

### Чого ви навчитеся

- Багатоплейсхолдерний `PREPARE`.
- Порядок значень у `EXECUTE … USING` відповідає позиційним `?` в тексті SQL.
- Що один підготовлений запит можна виконати багато разів з різними значеннями — без повторного парсингу.

### Задіяні таблиці

| Таблиця | Колонки |
|---|---|
| `work_orders` | `id`, `status`, `total_cost` |

### Завдання

Підготувати `'SELECT id, status, total_cost FROM work_orders WHERE id BETWEEN ? AND ? ORDER BY id LIMIT ?'`. Прив'язати `@p_lo := 100`, `@p_hi := 400`, `@p_lim := 8` і виконати.

### Очікуваний результат

```text
+-----+---------------+------------+
| id  | status        | total_cost |
+-----+---------------+------------+
| 100 | cancelled     |     510.00 |
| 101 | new           |     510.10 |
| 102 | in_progress   |     510.20 |
| 103 | waiting_parts |     510.30 |
| 104 | completed     |     510.40 |
| 105 | cancelled     |     510.50 |
| 106 | new           |     510.60 |
| 107 | in_progress   |     510.70 |
+-----+---------------+------------+
```

### Підказка

`EXECUTE stmt USING @p_lo, @p_hi, @p_lim` — порядок **має** збігатися з `?` у `WHERE id BETWEEN ? AND ?` і `LIMIT ?`.

### Розв'язання

```sql
SET @sql := 'SELECT id, status, total_cost
             FROM work_orders
             WHERE id BETWEEN ? AND ?
             ORDER BY id
             LIMIT ?';

SET @p_lo  := 100;
SET @p_hi  := 400;
SET @p_lim := 8;

PREPARE stmt FROM @sql;
EXECUTE stmt USING @p_lo, @p_hi, @p_lim;
DEALLOCATE PREPARE stmt;
```

### Покрокове пояснення

1. **Побудуйте SQL** у `@sql`. Три `?` позиційні.
2. **`EXECUTE … USING @p_lo, @p_hi, @p_lim`** прив'язує **у порядку**. Поміняти `@p_lo` і `@p_hi` місцями — отримаєте порожній результат (жоден рядок не задовольняє `BETWEEN 400 AND 100`).
3. **Повторне виконання з новими значеннями без повторного `PREPARE`:** `SET @p_lo := 200; SET @p_hi := 250; EXECUTE stmt USING …;` — той самий план, інші значення.
4. **`DEALLOCATE PREPARE stmt`** звільняє назву запиту. Забути — у короткому скрипті здебільшого безпечно, але у тривалих з'єднаннях накопичується.
5. **Безпека:** підготовлені запити з `?` — стандартний **захист від SQL-ін'єкцій**, коли параметри керуються застосунком. Не вставляйте користувацький ввід у `@sql` через `CONCAT`.

## Вправа V7 — Системні змінні (`@@version`, `@@session.transaction_isolation`)

### Контекст

DBA хоче переконатися, до якої версії сервера підключений клієнт і на якому рівні ізоляції транзакцій працює сесія, перш ніж запускати чутливу міграцію.

### Чого ви навчитеся

- `@@x` читає **системну** змінну (не користувацьку).
- `@@session.x` — значення для з'єднання; `@@global.x` — значення за замовчуванням для сервера.
- Кілька корисних: `@@version`, `@@session.transaction_isolation`.

### Задіяні таблиці

(без бізнес-таблиць — лише метадані системи)

### Завдання

Повернути таблицю `metric` / `value` з версією MySQL і поточним рівнем ізоляції транзакцій через `UNION ALL`.

### Очікуваний результат

```text
+---------------+-----------------+
| k             | v               |
+---------------+-----------------+
| mysql_version | 9.6.0           |
| tx_isolation  | REPEATABLE-READ |
+---------------+-----------------+
```

### Підказка

`SELECT @@version` і `SELECT @@session.transaction_isolation`.

### Розв'язання

```sql
SELECT 'mysql_version' AS k, @@version AS v
UNION ALL
SELECT 'tx_isolation'  AS k, @@session.transaction_isolation AS v;
```

### Покрокове пояснення

1. **`@@version`** — це коротко для `@@global.version`; версія сервера.
2. **`@@session.transaction_isolation`** — рівень ізоляції **поточного з'єднання**. Змінити для сесії: `SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED`.
3. **`UNION ALL`** склеює два одно-рядкові запити в одну охайну таблицю результату. `UNION` (без `ALL`) прибрав би дублікати — тут не потрібно, обидва рядки різні.
4. **Тільки читання у звичайних лабораторіях:** для зміни `@@global.*` потрібен `SUPER` (або `SYSTEM_VARIABLES_ADMIN`). Скрипт лише **читає** значення.
5. **Варіанти:** `SHOW VARIABLES LIKE 'version'` повертає те саме, що `@@version`, тільки як рядок, а не скаляр.

## Вправа V8 — Очищення користувацької змінної

### Контекст

Скрипт раніше задав `@avg_cost`, і ви хочете явно показати, що значення більше не актуальне (наприклад, переходимо до нового логічного кроку). Присвоєння `NULL` — звичний «скид».

### Чого ви навчитеся

- Присвоєння `NULL` помічає змінну як «очищену», але ім'я лишається в сесії.
- Перевірка `@x IS NULL` повертає `1` (істина) при очищенні.
- Закриття з'єднання очищує все автоматично.

### Задіяні таблиці

(без бізнес-таблиць — лише стан сесії)

### Завдання

`SET @avg_cost := NULL`, потім перевірити через `@avg_cost IS NULL` і стабільну одиницю — підтвердити, що сесія жива.

### Очікуваний результат

```text
+------------------+-------+
| metric           | value |
+------------------+-------+
| avg_cost_cleared |     1 |
| session_ok       |     1 |
+------------------+-------+
```

### Підказка

`@avg_cost IS NULL` повертає `1`, коли змінна очищена.

### Розв'язання

```sql
SET @avg_cost := NULL;

SELECT 'avg_cost_cleared' AS metric, @avg_cost IS NULL AS value
UNION ALL
SELECT 'session_ok'       AS metric, 1                 AS value;
```

### Покрокове пояснення

1. **`@avg_cost := NULL`** не видаляє ім'я зі сесії — лише ставить значення `NULL`. Еквівалент «забути закешоване значення».
2. **`@avg_cost IS NULL`** дає `1` (істина). `IS NULL` — єдиний спосіб перевірити на `NULL` (`= NULL` сам повертає `NULL`).
3. **Повний скид:** від'єднатися і перепідключитися (`DISCONNECT`) або перезапустити клієнт. У MySQL немає `UNSET @x`.
4. **Завершальна `1`** виконує роль сигнальної мітки — у скриптах останній рядок завжди щось друкує, і запускач знає, що виконання дійшло до кінця.

## Розв'язання проблем

| Симптом | Що зробити |
|---|---|
| `@x` дорівнює `NULL` після скрипта | Змінні живуть у з'єднанні — ви перевідкрили клієнт. Перезапустіть `SET`. |
| `LIMIT @offset, @count` дає помилку | `LIMIT` не приймає змінні в чистому SQL. Загорніть у `PREPARE` / `EXECUTE` (V3, V6). |
| `EXECUTE stmt USING @a, @b` скаржиться | Кількість прив'язок має дорівнювати кількості `?`. Перерахуйте уважно. |
| `@avg_cost` має зайві нулі | Користувацькі змінні зберігають десяткові з більшою точністю, ніж стовпець. Загорніть читання в `ROUND(@avg_cost, 2)`. |
| Лічильник `@rn := @rn + 1` «перескакує» номери | Не зробили ініціалізацію через `(SELECT @rn := 0)` — змінні ініціалізуються ліниво, і застаріле значення з попереднього запуску просочується. |

Щоб запустити **всі** приклади одразу: `mysql -t -u root car_service_db < 03_mysql/11_variables/car_service_variables_examples.sql`.
